## 1. 案例、运行与云资源是三种不同计数

正式评价包含 **20～30 个独立人工构造案例**。设计不把它变成 20～30 台 VM，也不把 3～10 个合成资产的规模假设当最低云资源要求。

| 对象 | 标识与冻结内容 | 计数规则 |
| --- | --- | --- |
| CaseDefinition | case_id、输入／业务版本、scope、可查信息、问题族标签、信息充分性、预期证据与建议判据 | 独立配置／业务情形才是新案例；仅改名称、重复运行不增加数量 |
| EvaluationProtocol | protocol_version、案例集合、调试／正式分割、各组提示词、模型配置引用、采样、工具／投影版本、预算、评分匹配规则 | 正式运行前冻结；调整后另开版本，不用测试集答案调提示词再回填旧成绩 |
| EvaluationRun | run_id、case_id、arm、repetition、冻结输入摘要、共同规则结果摘要、状态／错误和实际开销 | 三组的每次执行分别记录；重复记录不冒充新独立样本 |
| RealEnvironmentEpisode | episode_id、真实对象引用、基线／前后快照、人工操作声明及时间、采集记录、还原／清理记录 | 同一台 ECS／同一套防火墙可对应多个串行情境；不是人工案例主体数量 |

调试案例与最终评价案例名单分开。真实脱敏材料单列为补充；当前原型样例、文档校验负例和接口单测不自动计入 20～30 个正式评价案例。

## 2. 三组通过同一服务边界，改变的只是模型编排

| 组 | 执行方式 | 模型／工具与结果约束 |
| --- | --- | --- |
| rules_only | 加载固定输入和共同确定性规则结果，生成基础输出 | 模型 HTTP 次数为 0；不要求配置同模型，不为“公平”补做模型调用 |
| fixed_model_pipeline | 预先冻结的步骤通过受控 QueryService 获取资料，再调用模型 | 读取步骤来自预定义流程而非模型选择；仍受同工具权限、字段投影和预算限制 |
| agent_tool_selection | 同一模型依据已得信息选择工具与后续补查 | 保存实际 call ID、输入依赖和选择来源；不把强制脚本顺序冒充自主选择 |

纯规则组保留已有规则定义中的基础解释与条件模板，不为突出模型效果人为清空。三组共享这些基底；模型新增推断／建议另外记录与评分，没有产生某类输出时明确标不产生，不伪造零风险或满分。

三组共用同一规范分区、快照／业务版本、评估时点和规则结果。先准备并冻结规则结果，分别让各组引用其摘要；任何模型输出不能修改该结果。固定模型流程与 Agent 采用相同模型配置引用、采样、初始信息、可访问数据、工具权限及上限，实际取得证据和实际开销可以不同。

“相同初始信息”指编排开始前的共同 brief／规则摘要；工具读取后上下文可不同，协议须记录时序，不声称每次 HTTP 请求体完全相同。固定流程步骤在调试阶段冻结，不依据正式案例答案选择资料；标签仅给评分器，不能进入任何模型提示词或工具返回。

固定流程的预取也记录为工具／查询步骤，计入相同访问预算，`selection_origin=predefined_pipeline`；Agent 的选择记录为 `model`。不得给固定组或 Agent 额外隐藏事实。一次性输入全部材料的 LLM 仅可作为已说明不同条件的附加参考，不取代这三组。

评价执行器是 **G2 后的实验适配器**，复用应用服务、规则结果和 QueryService；不是新增产品页面、公开 API、Agent 或微服务。正式产品继续只提供既定规则／Agent 模式，不为论文加入可绕过权限的“实验后门”。具体执行命令在实现并验证后再提供。

## 3. 标签与三类输出分别评分

### 3.1 规则事实

- 主匹配键为 `case_id + asset/service 或 gateway subject + 预冻结业务问题族`；相关 CHK 指向同一问题只计一次，原始规则记录另留。
- 在可判定正负样本中报告 TP／FP／FN 与 Precision／Recall／必要时 F1；分母为零为“不适用”，不记满分。
- 信息不足、应待确认、明确不支持的案例单列，不混入已确认正负样本来美化风险识别成绩。
- 三组若使用同一规则结果，其规则事实指标理应相同。不能将模型补充或少查数据带来的差异包装成“规则准确率提升”。

### 3.2 模型推断

独立保留模型疑点、依据引用、错误确定断言、正确保持待确认和无效输出。模型新增错误不能被共同规则结果掩盖；输出校验拒绝也应进入失败／无效计数，而不是悄悄删除该运行。

### 3.3 配置建议

按需求既定四项逐项记满足／不满足／无法判断：对象正确、证据支持、满足业务约束、没有新增超出授权的开放。先用预定义约束校验，再人工复核并记录说明；可有第二人复核部分样例，但不伪造专家或外部独立评审。

格式合法或被模型自己打高分不是建议正确；“采纳为本地待办”也不是云上修复证据。依赖未知时，合理的条件建议可以合格，不强迫输出具体网段。

## 4. 全部运行保留，统计总数可对账

`EvaluationRun` 至少保存：

- protocol／case／arm／repetition，实际输入与共同规则结果摘要，模型／提示词／工具／字段投影配置引用。
- `completed / partial / failed / cancelled / interrupted`、超时／预算等原因；没有输出时标 `output_absent`，不记作“零风险”。
- 各类输出引用及可评分性、未完成部分，原始匹配计数、人工评分说明和版本。
- 排队／执行墙钟、阶段耗时、真实工具步数、模型／云 HTTP 尝试与可得 usage；没有返回用量时为 unknown，不补成 0。

全部正式运行数必须等于各终态数量之和。完成率／失败率使用全部正式运行作为分母；partial 等状态分别报告，失败归因定义在协议里固定，不只统计成功输出。对已产生的部分结果可分层评分，但必须同时展示未产生／不可评分数量，不能把失败案例从数据集中移除。

独立案例数、每案例重复次数和总运行数分开。代表案例和重复次数事前确定，实际执行仍须独立预算授权；不强行重复大量次数追求统计显著性。

公开材料只保留人工输入、冻结标签、运行标识、受控输出与计数。云凭据、精确私有端点、原始模型 wire／reasoning 和未脱敏真实数据不公开；模型配置引用用于证明两组条件一致，公开摘要不包含密钥值或密钥哈希。实际货币费用依真实服务账单，不由 token 字节数或尝试次数推算成已知金额。

## 5. 串行真实验证与至少一次整改复审

默认资源安排：**优先同一台 ECS／同一套云防火墙复用**。NAT 所需网关、公网与关联资源另列最小清单，在实际执行前核对权限、能力、保留时间和预算；不把“复用一台 ECS”误解为不需要 NAT 边界验证。

每个真实情境按以下步骤串行执行：

1. 操作者确认资源、范围与当次权限／预算，记录 baseline 配置和 episode_id；不在生产敏感服务上为展示效果制造危险配置。
2. 系统按只读连接采集，保存 `live_readonly` 来源、时间、完整性和资源／分区证据，完成首次审计。
3. 操作者在系统之外进行已授权的受控配置修改，记录修改对象、说明和完成时点；系统没有云写或自动清理工具。
4. 以明确的 force_refresh／fresh_after 重新采集同一规范分区，获得新的不可变输入，再次审计。
5. 按一致对象、规则／业务基线及观察点比较，保留改善、仍存在、新增和不可比较的原因；对象丢失／缺页／边界变化不记成已修复。
6. 保存前后输入、审计／报告、人工修改声明和比较证据；操作者还原／清理本例配置后再开始下一例。还原／释放同样是人工操作，不新增系统写权限。

至少一次上述真实链路要实际完成并有可核验证据；模拟与离线不能替代 AC-10。若产品、权限或预算条件不具备，只能记录相应接入／复审未验收，并由用户决定后续安排，不能据此宣布整体验收完成。

同一资源 ID 在不同 episode 下有不同版本，不互相覆盖；同一真实 episode 中的多次运行也不自动成为多个独立人工案例。角色差异可在离线输入表达，不要求为每个角色实际部署服务或并行开 VM。

## 6. 验收材料与执行顺序

| 材料 | 对应验收 | 当前状态 |
| --- | --- | --- |
| 20～30 个独立人工案例、冻结标签和协议 | AC-21、NFR-07 | 待 G2 后构造与复核；不是现有静态示例数量 |
| 三组原始运行、全部终态、重复记录与分层评分 | AC-21 | 待执行；纯规则不调用模型 |
| 至少两种真实工具路径，其中一种依赖前次结果 | AC-06 | 旧 MiniMax 两例只有一批工具，不替代此项 |
| 审阅保存／失败／刷新重启与报告固定版本记录 | AC-15 | 待正式存储与 UI 验收 |
| 真实前后快照、人工修改、重采集与复审证据 | AC-02／10 | 未执行；串行资源复用不降低边界覆盖 |

实现顺序：纯 Go／协议基础门槛 → 规则和输入 → 持久服务／Web → 受限 Agent 与三组执行适配 → 授权真实接入与复审 → 冻结并执行正式评价。调试与正式评价明确分离；没有 G2 时本轮只做设计与静态校验。
