# 会话、任务执行与恢复设计

基线：需求v0.6／B2、设计v0.6，G1／G2已通过。本文为该领域的现行详细设计；实际运行验收另行取证。

## 1. 业务模型：连续会话，不是孤立任务列表

首版以一个默认审计空间组织来源、范围、画像和基线，不建设复杂项目／组织管理。空间中可以有多个命名会话；同一会话多轮沟通共用已确认业务资料，引用历史任务／报告。任务只是一次有范围、有预算的执行，不等于一个新会话。

人工业务例子：

1. 用户在会话 S1 导入／选择三台 VM，自动线索已存在则不重收集、不重复询问；模型提出候选，用户确认角色／必要访问。
2. 用户继续问“为什么数据库有这个问题”，本方案引用上次审计的版本和证据解释，不自动刷新全部云资源，也不丢掉前轮确认。
3. 用户在云平台手动修改后要求复审，明确选择强制刷新；新快照就绪后产生新审计版本，旧报告／消息仍可查。
4. 浏览器刷新或应用重启后可重新打开 S1，看到消息、资料确认、阶段结果、报告及中断记录。应用访问仍按安全策略解锁，但历史不会因此重置。

## 2. 持久化层次与边界

| 层次 | 保存什么 | 不做什么 |
| --- | --- | --- |
| 审计空间 | 默认来源／范围、资料指针、基线和会话列表 | 不把它变成云上租户、组织权限或多账号治理平台 |
| 会话 | 标题、范围、偏好数据策略、上下文摘要位置、最后访问及归档状态 | 不每次发送就新建，不把新会话当预算重置接口 |
| 用户可见消息／轮次 | 用户正文、助手公开答案、引用／待确认卡片、用户确认事件、关联任务、状态和时间 | 不保存密钥或完整内部推理，不把助手建议写成业务授权 |
| 执行任务／阶段 | 请求、数据计划、固定后最终输入、规则／工具事件、尝试／耗时／用量 | 不用执行记录替代可继续对话的消息历史 |
| 资料／证据／报告 | 不可变快照、画像／授权版本、原始规则发现、报告和本地审阅历史 | 新资料不覆盖旧输入，归档会话不级联删除证据 |

入库前拒绝／屏蔽系统已知凭据值和明显密钥输入，正文不先写日志；不能保证识别用户随意贴入的一切未知秘密，界面始终说明不要在聊天贴密钥。消息保存到私有业务库，刷新／重启后由 API 分页加载，不依赖浏览器 localStorage。可见助手正文为本地私有历史，公开报告仍默认采用白名单结构，不能因历史存在就把自由文本导出。

明确发送带 `client_message_id`、当前范围／投影及 `model_use_accepted`，由统一准入生成内部执行计划并与幂等意图绑定；用户消息、轮次、排队执行引用一次事务落地，避免超时重发产生重复消息／模型请求。同会话首版只允许一个未结束的 queued／running／cancelling 执行；新输入可等待、保存草稿或由用户显式取消前轮后发送，不能默认自动抢占／重放；本地确认、审阅与历史读取不占执行槽位。不同会话使用3个并行执行槽位；前3个会话可同时推进，槽位占满后后续会话明确排队，不把多标签页等同于业务并发。

## 3. Eino 的职责：历史、上下文与 Checkpoint 分开

F-08 官方示例明确由业务层管理 Session／Memory／Store，再把消息交给 Runner；F-09 的 CheckPointStore 是中断／恢复运行的可选接口，不规定 SQLite、GORM 或固定表结构。本方案还只读核对固定 v0.9.22 的 RunnerConfig／Run，未修改依赖。

### 3.1 首版选择

- 应用用 GORM／私有库保存可继续沟通的业务历史、确认事实与版本；Eino 负责当前有界轮次内的模型／工具循环。
- 每轮 ContextBuilder 从同空间／会话取当前分区与外发政策允许的最近消息、分区摘要、已确认事实和被引用报告，形成本方案可授权上下文；不是只发最后一句，也不每次把全部历史／原始云数据重发。
- 同轮按模型协议需要在内存保留完整 assistant／工具关联及必要 reasoning；结束后仅保存公开答案、受控工具摘要与引用。
- 首版不持久化完整框架 checkpoint。运行中重启标中断、保留已落地历史／证据，用户可以继续会话，但不会自动重放上次未完成的付费调用。
- Eino TurnLoop 等可用于执行控制，但不是会话数据库；不能不加区分地让普通追问抢占正在采集／审计的任务。是否采用具体控制 API 在固定版本构建时验证，不用最新版示例替代项目兼容验收。

### 3.2 历史回放与新事实

不将截断的旧 assistant 工具调用和孤立 tool 消息拼成“完整协议历史”。重建时使用公开对话内容和证据摘要；必要时把它们作为引用上下文，不复用旧 tool_call_id 或缺失 reasoning 的原始协议片段。

ContextBuilder 按预算选择最近公开消息与摘要，并总是从固定业务版本取得必要约束。历史过长明确记录未带入范围，不丢掉确认约束后假装上下文完整；优先从结构化资料生成摘要，不每轮额外调用模型总结。助手旧答案仍是历史解释，不自动变成当前事实。

用户补充但尚未确认的信息停留在草稿。换快照、标签变化或业务版本变化时展示差异／冲突，不静默覆盖已确认内容；“解释昨天的报告”沿用昨天的绑定，“核查现在”需要新的数据计划。

## 4. 数据策略：不能每次全量实时收集

| 策略 | 业务用途 | 行为与结果标识 |
| --- | --- | --- |
| `pinned_snapshot` | 解释／复验指定历史结果，离线模式 | 固定版本，不自动云查询；显式显示时点和历史性质 |
| `prefer_fresh`（建议默认） | 日常审计 | 当前分区所需数据族满足策略则复用；否则做一次有界刷新。失败不默认把陈旧缓存当新数据 |
| `force_refresh` | 人工变更后复审、用户明确要求当前采集 | 绕过满足时效的旧缓存；如有 fresh_after 要求，采集批次不得早于该要求 |

`allow_stale_fallback` 默认 false。刷新失败时保留失败／部分结果；用户可明确新建使用旧快照的历史分析，或者在发起前显式允许缓存回退。回退必须持久化标识和数据年龄，不据陈旧缓存声称当前已修复。

### 4.1 时效与完整性是不同维度

完整但陈旧、最新但漏页都不能混同。默认时效提案：CFW 策略／保护／引用配置族与安全组配置约 15 分钟，实例名称／标签等低频元数据约 60 分钟；仅为可配置工程初值，不是厂商 SLA、法定保存期限或当前实测结果。业务授权和例外按版本／有效期判断，不用缓存 TTL 代替审批。

每个规范分区的 CFW 策略、保护与引用作为同一配置族收集／复用，不能任意拼“新策略＋旧地址簿”后证明路径。云查询不是原子快照，保留各分区／分页的采集窗口、过滤与一致性限制；数据族年龄按最老必需分区保守判断。复用旧分区保留其原时点，不能用本次快照创建时间给旧事实“续新”。

允许复合快照引用有各自 provenance 的不可变数据族；是否物理去重由存储实现决定，时点／版本信息不能丢。实例关联改变时对应安全组上下文失效；模型只从已封存输入读数据，不在同一审计中偷偷切换最新快照。

### 4.2 定时采集是可选产品能力，不是自动付费审计

架构允许本进程调度按已授权来源／范围刷新快照，默认关闭，初版 M0 先做人工／按需刷新与复用。操作者明确开启后才周期读取；定时采集不自动调用模型，也不自动运行策略变更。

后台优先级低于用户任务，只在空闲或下一领取点参与；同来源／范围／配置版本的待采集请求合并，避免手动与定时重复读。重启跳过错过的周期，不回补请求风暴；刷新有次数、间隔、分页、凭据及总时限。首版不引入外部队列、集群 leader 或 Codex 自动化。

## 5. 输入绑定：请求先冻结，实际输入稍后封存

支持按需刷新后，旧设计“接收请求即绑定一个实际快照”不再适用于所有模式，故分两层：

1. `request_manifest` 在受理时不可变：空间／会话／资产范围、数据策略、确认资料基版本、基线／模型配置引用、外发政策、预算和用户意图。
2. `data_plan` 记录预计复用／需刷新数据族和原因；计划与实际结果分开。
3. 可选采集和归一化完成、进入规则阶段前，生成一次 `resolved_input_manifest`：实际快照／分区时点、固定业务／规则／规范化版本及 evaluation_at。之后不可替换。

默认评估时点为进入分析的时点并封存；明确复验可引用原值。排队时旧资料被修改，仍使用请求锁定的确认版本并提示，不悄悄改为最新；若实际新资产／新线索与基版冲突则标待确认。

有界工作器池下，audit 如需刷新，在本次执行的采集阶段内调用采集服务，**不创建子 collect 入同一队列再同步等待**。若先前独立 collect 已完成则按数据策略复用；相同待执行后台采集可被本次产物满足。所有阶段共用根预算，不给子阶段新额度。

## 6. 累计耗时与执行预算

用户等待时间不是模型某一次超时。需分别记录：

```text
总墙钟时间 = 排队 + 准备/认证所在阶段 + 采集关键路径 + 归一化/规则 + Agent循环 + 校验/报告
外部请求累计耗时 = 各云HTTP、凭据交换、模型HTTP（将来MCP）的实测耗时之和
```

并行查询有重叠，累计请求耗时可以大于墙钟时间，不能直接相加当成用户等待时间。认证／SDK续期计入所属阶段，重试退避也计时；不要把嵌套阶段重复加总。保存排队／阶段起止、缓存命中、实际尝试、可得用量和错误，不能拿缺失 usage 当零。

### 6.1 G2 批准方案下的统一工程上限

| 类型／阶段 | 默认上限提案 | 约束 |
| --- | --- | --- |
| 新建受理／历史读取 | 短 HTTP 请求，返回任务／轮次引用；本地读取目标另测 | 不等待全流程；HTTP request context 不作为异步任务生命周期 |
| audit 排队／执行／受理到结束 | 120 秒／240 秒／360 秒 | 排队超限不发外部请求；执行阶段和子调用受根剩余时间约束 |
| audit 内采集含认证／规则含语义归一化／模型／最终化 | 90／20／120／10 秒 | 串行阶段合计 240；省下时间可提前结束，不在错误时自动扩时 |
| 助手轮次排队／执行／总计 | 60／90／150 秒；云 HTTP 上限 0 | 助手轮次禁止隐式刷新云，缺资料返回单独的采集预览；模型阶段仍受每次请求和总尝试限制 |
| 独立 collect 排队／执行 | 120／90 秒 | 全部认证、读接口、退避、解析都在执行预算内 |
| 显式 connection_check 排队／执行 | 60／30 秒；最多 6 次云／凭据 HTTP 尝试 | 仅身份与所选产品的有界只读探测，不做完整枚举；成功不表示全部接口权限通过；config-check 本地无外呼 |
| 不同会话任务并发／每会话未结束任务 | 3／1；另有等待队列10 | 禁止全局串行；第4个任务等任意空位，历史／审阅不占任务槽位 |
| 全应用云／凭据实际 HTTP 并发 | 最多 2 | token 依赖分页仍串行；含续期，共享限速和尝试预算，不复制刷新风暴 |
| 全应用模型 HTTP／单任务模型 HTTP 并发 | 3／1 | 允许3会话真实重叠；资源等待计阶段／根剩余时间，不追加次数／费用授权 |
| 模型单次／助手轮次HTTP尝试／审计模型HTTP尝试 | 30 秒／4／6 | 用户私有配置更严时优先；每个实际尝试计数，非成功次数／金额上限 |

这些不是已测响应时间或当前付费授权。SDK 获取凭据和 HTTP 可能有独立超时／重试，必须纳入适配与测试；不能仅给业务函数套协程超时，就声称底层请求已取消。服务端队列采用 typed job context 与剩余 deadline，不能把 Gin 已结束／被复用的请求上下文传给后台。

同会话累计尝试／用量和任务开销可查，新开会话不应成为绕过应用预算的方式；执行级硬限制、会话预算策略与全应用限额分层取更严值，金额仍以供应商账单为准。明确新任务是新的执行意图，不通过刷新页面／恢复历史重新消费。

## 7. 分层输出，而不是一直等待最终模型回答

| 层 | 何时展示 | 必须标明 |
| --- | --- | --- |
| L0 计划／排队 | 受理后 | 拟复用／刷新哪些数据、范围、预算、等待状态；计划不是模型已执行步骤 |
| L1 事实／完整性 | 读取缓存或采集就绪 | 来源、数据年龄、缺口；缓存预览不是本次已封存输入 |
| L2 确定性结果 | 规则阶段落地后 | 规则事实与待确认项，Agent 补充待完成；可先审阅，不等模型 |
| L3 Agent 补充 | 经过校验的工具／公开结果就绪 | 已执行工具、引用、角色候选／条件解释与错误；不展示完整内部思考 |
| L4 汇总／报告 | 终态结果就绪 | 固定输入、覆盖、阶段失败、本地计划及复审关系，不因部分失败抹掉 L2 |

首版用持久有序事件＋fetch SSE 主通道／JSON 轮询兜底推进，不依赖模型 token 流式；完整协议、重连与终态规则见 [前端与事件](frontend-and-events.md)。订阅／重连仅恢复观察，不重放旧工具消息或付费请求；断线不取消任务，页面恢复不清零预算。阶段名、已知对象／已执行检查数、累计耗时可以显示；无法估计时不伪造百分比或倒计时。任务 running 时 `result` 返回 `is_final=false` 与已完成阶段，正式报告终态生成；如未来导出阶段报告，必须独立版本且标未完成。

默认3个槽位使不同会话可真实同时推进，而不是以后再考虑并发。历史读取／审阅不占任务槽位；共享模型HTTP最多3、云／凭据HTTP最多2，预算与时限分层取严。固定并发、输入／Runner隔离、有界资源等待和三请求屏障验收见[总体架构](architecture.md)。

## 8. 待实施验证

- 持久历史：刷新／重启后重开会话、继续问答、引用旧报告；不重放中断调用或将旧答当当前事实。
- 协议与上下文：不孤立回放 tool 消息／缺失必要协议字段；长历史受控裁剪仍保留确认约束，未确认对话不成为授权。
- 缓存：合格命中零新增云查询；陈旧／未知时点、部分配置族、人工变更后强制刷新、失败回退显式且不声称当前修复。
- 累计时间：模拟多次各自未超时但总时限超出的接口、STS 续期、退避、排队和模型链，验证根预算与 L2 保留。
- 后台调度：默认关闭，前台优先、去重、重启不补历史周期，不自动触发模型。
- 三槽位工作器池：3会话真实重叠、第4个等任意空位、同会话1任务；需刷新时不等待自己队列中的子任务；HTTP 202 返回后执行仍合法，显式取消与服务停机能终止后续请求。

上述为正式实现后验收计划。当前离线原型不具备服务端历史、新鲜度调度、真实对话和累计外部调用计时。

跨入口起点／续聊／阶段失败的推荐短语见 [用户引导](guidance-and-entrypoints.md)；引导目录本地生成，不为首次欢迎或每次建议额外调用模型。

## 9. B2 的分区缓存与计划时效

### 9.1 缓存键与就绪条件

缓存合格键至少包含连接配置／期望账号引用、规范 policy_scope_key、采集 schema／normalizer／provider_semantics 版本与必要对象选择。互联网 in/out、不同控制面或两个 NAT 网关均不得命中同一策略配置族；不能因为 asset_ids 相同就复用。

NAT 配置族包含当前网关元数据／ACL／静态引用／模式，资产上下文与 NAT 关联证据作为另有时点的族。首次基线仍建议配置族 15 分钟、低频实例元数据 60 分钟；关联改变或 owner／模式变化要使有关计算输入失效。TTL 合格不代表成员完整、账号正确或两次观察稳定。

真实只读刷新默认最多两轮完整配置族读取，形成 observed_stable／changed／unverified。仅两次相同不声称原子快照；已知变化或第二轮未完成使受影响配置路径保持部分结果。固定离线制品可记 fixed_artifact，不伪造复读；来源真实性／全量性仍独立判断。所有 API、认证与重试都计入原 100 次／90 秒采集上限；第二轮不获得独立预算。见[云采集设计](aliyun-collector.md)。

### 9.2 预览计划与执行阶段的关系

`execution_plan` 是本地预览和效果授权的记录，建议 5 分钟有效；`data_plan` 是预计及执行时实际复用／刷新选择。用户确认有效计划后，创建 job 的时点才开始计算排队／根时限，不把用户阅读预览的时间伪装成服务执行时间。

计划中的 prefer_fresh 必须预先说明可能刷新；执行时缓存因排队过期，可以在已批准效果上限内更新 data_plan，不能改 request_manifest 的 scope／模式／预算。pinned_snapshot 的云读取上限为零，绝不能自动升级为实时采集。force_refresh 不以旧缓存满足 fresh_after。

计划消费后按原幂等键重试返回原 job；更改连接配置／范围／业务版本的请求必须重新预览。手工修改配置产生新修订号；Provider 合法 STS 续期不是换账号或自动扩权，但也计入根预算。排队时配置版本已失效则停止并提示，不偷偷改用最新连接。

运行中的 deadline 使用进程单调计时并受剩余时间约束；queued 的受理／到期时点持久化，重启只续仍有效的排队记录，运行中任务标 interrupted 不重放。时钟信息无法确认时不延长额度。

### 9.3 反馈与验收

L0 明确本次分区、网关／资产模式、预计复用与允许外呼；L1 展示各族原始窗口、稳定性与缺口；L2 保留已计算事实；L3 模型补充不替换分区；L4 报告固定完整 scope 和输入。切换边界是新计划／新任务，不改写历史消息里的旧证据。

验证计划为 B2-11／12／15／16 和原 RC-21～24。本方案静态示例校验不执行缓存、SDK 取消或计时测试。

### 9.4 持续会话的范围隔离

切换分区不删除业务会话，但模型上下文不能直接复用整个会话的原始历史／全局摘要。摘要按 conversation＋规范 scope＋disclosure 版本保存，并记录覆盖消息位置；其他网关／方向的助手事实与工具衍生信息不进入当前输入。当前 scope 的历史仍可连续使用，跨 scope 内容在 UI 保留本地链接。

B2-17 增加“同一会话先审网关 A，后审网关 B”的输入检查：不仅工具要拒绝读 A，上下文和摘要也不得偷带 A 的非授权事实。旧报告追问使用报告固定 scope；不会重放旧 tool 消息或隐藏扩权。

## 10. 持久审阅、准入与工作器恢复（RV4-03／04／06）

### 10.1 审阅也是业务历史

意见与采纳／暂缓理由关联原 finding／job 和 review_revision 持久追加。确认提交完成后才提示已保存；保存失败、响应未知或旧修订冲突时保留草稿，不用本地 UI 乐观状态充当已保存。刷新／重启从服务端恢复历史，旧报告仍绑定其生成时的审阅版本。细节见[数据与API](data-and-api.md) 第 11 节。

### 10.2 明确发送不是隐式刷新

所有执行都经过同一准入。audit／collect／connection_check 的外呼来自用户接受的限时计划；assistant_turn 的明确发送在同一事务产生内部计划，仅允许模型与本地固定资料，云请求上限为零。模型要求新云数据时只产生可审阅动作建议，不自建采集任务。

GET 引导、连接状态、预览、历史读取与保存审阅均不调用模型／云。可选定时采集继续默认关闭，若以后启用，采用已明确授权的 collect 效果，不获得模型权限。

### 10.3 排队与重启顺序

1. 进程先取得数据目录独占锁；第二实例失败退出，不修改第一个实例的 running 记录。锁实现须在目标 Linux／WSL 环境验收，不能用可遗留的普通“文件存在”假装可靠互斥。
2. 锁取得后检查 schema／连接约束，才把上次遗留 running／cancelling 标 interrupted，不回放调用。
3. 未过期 queued 保留原请求／预算；过期的 queued 在获取凭据前失败，错误码 QUEUE_DEADLINE_EXCEEDED。取消 queued 直接终态 cancelled；无需等工作器出队。
4. jobs 表是队列事实来源；入队时在同一短事务检查容量／会话槽位并写计划消费／消息／任务。内存通知只是唤醒，启动和周期扫描能发现已提交记录，不能因通知丢失丢任务。
5. 数据库或队列准入失败不出现已发送但无任务的半记录；界面保留草稿。worker 用条件更新领取任务，不能仅凭一次 SELECT 就认为获得执行权。
6. 运行取消返回“取消已受理／cancelling”，并关闭后续尝试准入；已有请求只能尽力取消，送达未知仍计次数。终态通过条件更新落地，迟到成功回调不能把 cancelled／interrupted 覆盖为 completed，也不能给已取消轮次补一条正常完成答复。迟到的尝试计数／费用信息可另记日志，不改写固定报告。

3个执行槽位和有界排队是首版基线，不是无限并发承诺；排队剩余时间与超时原因可见。新请求不自动抢占长审计，也不反复创建新任务试图绕过排队。

### 10.4 逐物理请求的持久预算

每次云、凭据交换或模型 HTTP 尝试在发出前原子预记，检查任务、用户已明确的批次／会话预算和应用更严上限。预记失败则不发请求；SDK 重试必须重新预记，不能把多次网络请求算成一次逻辑工具调用。

预算记录不随新建会话、页面刷新、配置 key 轮换或重启清零；预算周期／上限由明确配置或授权决定，不让模型或客户端自选新周期。未设置的应用级金额上限不能被描述成已提供全账户费用保证，调用次数与货币仍分开。

启动后送达／费用未知的尝试保守记为已用，不自动重发或返还次数。只有能证明尚未发出才允许按既定规则释放预留；首版可保守不回收，不能为了成功率自行加额度。公开记录只保留 attempt 状态／计数与受控错误，不输出密钥或原始服务正文。

## 11. 事件流 订阅生命周期

事件／可见消息先保存，浏览器后展示；非流式模型只有公开答复提交后产生 message_available，不伪造 token 增量。最后连续 seq 属于当前页面已应用的投影，不孤立持久化游标；刷新重新解锁后从历史恢复。隐藏页／切换路由只释放订阅；显式取消、任务 deadline 与服务停机保持原语义。

SSE 订阅寿命／心跳、重连退避与轮询间隔不增加任务执行额度或重置累计尝试。终态事件必须排空后再停订阅，重启遗留任务终态为 interrupted、不自动续跑。客户端实时／重连／兜底／需解锁状态和业务 running／partial／cancelled 分开显示；详细阈值与 V5 验收见[前端与事件](frontend-and-events.md)。

## 12. 并发与恢复联动

同会话一个未结束槽位不变，全应用从单工作器改为3槽位；共享费用预占必须原子化、凭据续期有归属、Eino状态不能跨任务复用。独占进程启动锁用于单机单实例，不用于锁住三个任务。WAL＋普通共享连接池、事件seq、忙等待与存储不可写故障均见[31 §2](architecture.md)。

正常停机停止新准入／外呼、尽力结束或中断活跃任务；不能写成功不谎报已持久。重启恢复全部未终态任务、不重放，queued保留旧预算。按常规流程做本地备份／恢复、错误诊断，不新增存储专项框架；见[31 §4](architecture.md)。
