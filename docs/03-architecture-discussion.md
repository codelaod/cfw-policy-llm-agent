# 架构与技术方案讨论稿

状态：候选设计，尚未选定语言、框架、数据库或模型。更新日期：2026-10-20。

## 1. 架构方向

```text
前端 Web（首选入口）             CLI（可选后续入口）
          \                       /
                  后端 API
                     |
             审计任务与应用服务
              /             \
       确定性规则引擎       Agent 执行器
              \             /     |
               只读工具与证据服务  模型适配层
                       |          |
               统一快照与对象模型  OpenAI 兼容接口
                  /         \      其他协议待扩展
          阿里云只读适配器    离线样例适配器
```

前端负责配置输入、进度和结果展示；后端持有云平台凭据与模型凭据，完成采集、任务执行和报告生成。规则检查、Agent 工具与报告共享应用服务，后续 CLI 复用服务或 API，避免复制一套审计逻辑。

单进程后端加简单持久化即可作为起点，任务执行方式需保证 Web 请求不会被长时间模型调用阻塞。是否需要外部队列，待真实耗时和并发需求出现后决定。首版不预设微服务、多 Agent 或分布式部署。

## 2. 统一数据模型的最小集合

| 对象 | 主要内容 |
| --- | --- |
| Asset | 云平台、账号/地域、资源标识、公网地址、用途、标签、保护状态 |
| Policy | 策略标识、边界/方向、来源、目标、协议、端口、动作、顺序、状态、生效时间和引用对象 |
| BusinessIntent | 资产用途、允许访问范围、管理白名单、例外与有效期 |
| Snapshot | 原始数据位置、采集时间、模式、分页结果、缺失字段与归一化版本 |
| AuditRun | 输入快照、模型/提示词/规则版本、执行状态、用量与错误 |
| Evidence | 证据编号、来源对象、字段或结果片段、采集时间与可追溯位置 |
| Finding | 检查项、对象、严重程度、判定状态、证据及解释 |
| Recommendation | 关联发现、建议差异、前提、业务影响与人工处理状态 |
| ToolEvent | 调用编号、工具、参数摘要、结果证据编号、时间、错误与重试 |

具体字段名和数据库表结构在接口验证后定义。保留厂商原始标识与必要原始数据，以便审计结论能回溯；脱敏数据和真实原始数据分开存放。

## 3. Agent 怎样发挥作用

先用可控流程保证基础采集和规则检查，再允许模型在限定范围内选择工具补查。模型具有实际决策空间，但不能跳过最小数据完整性检查或无限循环。

示例流程：

1. 后端建立快照，核对采集是否完整，执行所选规则并生成证据。
2. Agent 获取审计目标、业务意图概况、资产概况和规则发现。初始概况只说明详细业务资料是否可查；具体资产用途、白名单等通过工具获取。
3. Agent 根据疑点选择工具，查询目标资产、关联策略、地址引用或缺失的业务说明。
4. 获得结果后补充解释；还缺信息则明确列出缺口，或向用户请求业务说明。
5. 输出符合约定结构的发现解释和推荐，后端核验对象与证据引用，再生成报告。

至少设计两个有不同工具路径的案例：一个补查资产用途后生成具体建议；另一个因为业务白名单缺失而形成待确认项。仅把配置一次性送入模型，不作为 Agent 成功实现的判据。

建议工具包括 `list_assets`、`get_asset`、`list_policies`、`get_policy`、`get_business_intent`、`resolve_address_reference` 和 `run_rule_checks`。流量与命中统计工具按实际接口和产品能力选做。工具返回结构化对象、证据编号与完整性信息，不能只返回一段无法定位的文字。

工具仅允许读取当前任务授权的数据。设置调用轮数、时间、输出大小和模型预算上限；相同查询可缓存。接口错误和重试耗尽后保留部分结果，任务标记为部分完成或失败。

资源名、标签、策略说明等外部文本按数据处理，不能改变工具权限或系统指令。输出检查至少核对 schema、对象存在性、证据可引用性和业务约束。模型自报“置信度高”不能替代这些校验。

执行记录用于展示工具选择和证据流转，不要求存储或展示模型完整内部推理。

## 4. 规则、模型和人的职责

| 参与方 | 职责 |
| --- | --- |
| 规则引擎 | 解析已支持的策略语义，计算明确条件，输出可重复的发现与证据 |
| Agent | 选择补查工具、理解业务上下文、解释风险、组织有条件的推荐 |
| 后端校验 | 检查输出结构、证据、对象引用和基本约束，记录运行状态 |
| 人工 | 提供业务需求、确认例外、判断修改影响，在云平台应用建议并复审 |

简单数值比较、端口集合运算和地址范围比较由代码实现。推荐校验需要考虑所选场景的策略顺序与默认行为，不能仅靠模型声称“改完即安全”。知识库检索只在有明确规则文档或基线资料且确有需要时加入，不以 RAG、向量库或多 Agent 的数量衡量系统价值。

## 5. 模型适配边界

建议首个具体适配目标为 **OpenAI Chat Completions 兼容接口**，待技术方案阶段确认。配置候选包括服务端 `base_url`、`api_key`、`model`、超时、采样参数和能力开关；密钥不进入浏览器或版本库。

适配器需要处理消息、工具定义、工具调用、工具结果、最终输出、错误和用量。接入新模型时应验证工具参数解析、多轮工具结果回传、中文结构化输出与失败行为；不能因支持文本聊天就声称支持本系统 Agent。

对暂不支持工具调用的服务，明确报告能力不足。若后续提供固定流程模式，需在界面和实验中区分，不能默默当作 Agent 模式。

“Claude Code 标准”需要进一步明确：Claude Code 是编码 Agent 工具，和模型 HTTP 接口不是同一层。若目标是接入 Claude 模型，后续评估 Anthropic 模型 API 适配；若目标是集成 Claude Code/其 SDK，则是另一项集成工作。首版不以集成编码工具为前提，详见 [官方资料](06-references.md)。

## 6. 技术选型如何讨论

已确定的是前后端分离与后端统一审计服务，其余保持候选：

| 选型项 | 建议的比较方式 | 当前状态 |
| --- | --- | --- |
| 后端语言与 Web 框架 | 结合维护熟悉度，验证云 SDK、类型校验、异步任务和模型工具循环；Python 可作为优先调研方向 | 未定 |
| 前端语言与框架 | 围绕表格、任务进度、详情与报告页面选型；TypeScript 可作为优先调研方向 | 未定 |
| Agent 框架或自研 | 用同一小案例实现工具循环，对比代码量、状态可见性、协议适配和错误处理 | 未定 |
| 持久化 | 根据快照、任务、证据和复审需要，比较轻量关系库与文件快照组合 | 未定 |
| 前端进度更新 | 先明确任务状态协议，再决定轮询或服务端事件推送 | 未定 |

自研可从少量只读工具、有限轮数的执行循环开始；采用框架时也需要讲清工具契约、状态、终止条件及错误处理。后续选型文档应给出实际验证结果，不仅罗列流行技术名称。
