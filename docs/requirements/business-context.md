# 业务价值与资产角色

基线：需求v0.6／B2、设计v0.6，G1／G2已通过。本文为业务依据与画像要求；实际运行验收另行取证。

## 1. 业务背景与价值定位

### 1.1 问题背景

公有云环境中的网络安全配置由资产暴露、防火墙覆盖、访问控制、主机与应用防护以及日志审计等多个要素共同决定。运维人员不仅需要核对策略语法，还需要理解资产承担的业务职责、预期访问关系和实际防护状态。若缺少这些上下文，同一条允许规则既可能是维持业务的必要条件，也可能构成超出业务需求的暴露；配置中存在安全产品，也不能直接证明目标资产已被其有效覆盖。

主流云厂商已经围绕配置检查、规则使用分析、业务资产管理和安全调查提供相关能力。阿里云的安全组检查与安全运营 Agent、Google Cloud 的 Firewall Insights、AWS 的 Security Hub CSPM 控制项以及 Microsoft Defender for Cloud 的生成式安全建议摘要，分别体现了这些不同方向（A-10、A-22、B-03、I-02、I-03）。这些能力的存在说明，本课题应围绕实际管理问题和可验证的审计流程开展，而不应将“使用 AI 推荐策略”本身表述为首创。

生成式 AI 与工具调用方法为安全信息理解、跨资料补查及建议解释提供了新的交互方式；ReAct 等研究可作为模型根据工具反馈继续行动的方法参考（P-08）。但语言模型不能替代可确定的策略语义、业务授权或证据核验。因此，本系统拟采用规则判据与受限 Agent 协同的方式：规则计算有明确边界的事实与差异，Agent 根据疑点补充上下文，形成条件清晰、依据可查、由人审核的推荐。

### 1.2 本系统拟提供的价值

| 价值目标 | 需要形成的业务能力 | 后续验证方式，不是已取得成效 |
| --- | --- | --- |
| 明确资产与防护关系 | 展示资产角色、暴露与各层防护的已知／未知状态，优先识别明确覆盖缺口 | 构造开启、关闭、未知与范围不符的配对案例，检查是否正确区分 |
| 提高建议与业务的相关性 | 区分 Web、数据库、后台服务与未知角色，结合明确访问关系选择判据和建议 | 同一网络配置用于不同角色／访问要求时，结果应随有效上下文变化 |
| 降低上下文核对负担 | 将配置、业务声明、适用指南与可用日志证据组织到同一审计过程 | 记录补查路径、必要人工输入、耗时及错误；不预先宣称显著提升 |
| 控制整改风险 | 说明建议的前提、配套变更、影响及验证步骤，不直接下发 | 检查建议是否保持已声明的必要访问，并识别可能误拦截 |
| 支持审阅与复验 | 保存版本、证据和例外，区分事实、推导与未知，支持人工变更后复审 | 在固定案例上核对一致性、可追溯性与不可比较情形 |

项目定位为面向有限范围的、可解释且可复核的云防火墙审计与推荐原型，不替代完整 CSPM、CNAPP、SOC 或厂商全部安全能力。性能、准确性和效率收益均需由后续实验验证。

### 1.3 行业能力与本项目的边界

| 参考能力 | 可借鉴的方法 | 本项目不直接继承的能力 |
| --- | --- | --- |

| Microsoft 生成式安全辅助（I-03） | 自然语言摘要和建议理解，联系上下文 | 产品许可、接入范围和宣传的效率收益 |

## 2. 资产角色应如何确定

### 2.1 区分三个不同问题

1. **配置上能观察什么**：例如 ECS 标签、系统类型和所关联安全组的入向规则。这是角色线索，不证明实际运行进程或监听服务。
2. **业务上承担什么职责**：例如生产 Web 前端、订单数据库、后台工作节点。需要可追溯的业务确认或经批准的标签映射。
3. **哪些访问被允许**：来源、服务、协议／端口、环境与例外。这是访问授权，不能由角色、端口或历史流量直接推出。

一个 ECS 可承载多个服务和角色，故角色应能关联具体服务／端口与适用范围，不能将整台主机强制归为唯一类型。拥有公网 IP 也不意味着所有服务都需要公网访问。

### 2.2 产品边界与API线索

按用户要求，**云安全中心从当前方案移除**：不调用其 API、不安装其客户端、不以其指纹或付费采集作为必要／可选前提，不推荐为本项目开通该产品。已有 ECS／安全组数据可作为自动线索；不承诺所有调用免费，权限、频率和实际返回在后续只读验收核对。

| 可取得的信息 | 官方依据 | 业务用途与限制 |
| --- | --- | --- |
| 实例名称、标签、OS、地址、关联安全组／网卡 | A-11 `DescribeInstances` | 自动填充已存在事实；名称和标签可能过时，不能直接当作角色或授权 |
| 关联组的方向、协议、目的端口、动作、优先级、来源／引用 | A-12 `DescribeSecurityGroupAttribute` | 根据入向允许配置提出 Web／数据库等候选，保留拒绝和未知条件；不等于已发现监听服务或实际可达 |
| 网卡／安全组关联补充 | 必要时 A-27 `DescribeNetworkInterfaces` | 按所选实例补查，避免共享组、多网卡或组关联不完整时错误归属；不建设完整拓扑 |
| 原有本地已确认信息／受信标签映射 | 人工记录、已批准映射；标签方法参考 I-01 | 可提前填充并标明版本，只有缺失／冲突内容再引导用户确认 |

例如关联组允许 TCP 80／443 时可提出 Web 候选，3306／5432 时可提出数据库候选；这只是推断输入，不证明服务、具体数据库类型或业务批准。大端口段、共享组或 ALL 协议会降低区分度，模型应说明不确定性而不是强行分类。

### 2.3 推荐流程：自动取线索，模型引导，用户确认

轻量标注已获用户认可；业务上不应要求用户把 API 已能取得的信息重填一遍。建议“画像页面＋内嵌对话／确认卡”，表单作为同一业务流程的直接编辑方式，而非另起一套事实。

1. 自动取得实例与其关联安全组事实，展示来源、范围和缺口；不要求云安全中心或主动扫描。
2. 用户发起有界的候选生成／引导任务，模型结合标签、名称、OS 和安全组配置提出候选及证据。没有模型时直接人工标注。
3. 只针对会影响建议的未知项提问：实际角色／服务、是否需公网、实际端口、调用方／管理来源。用户可跳过或回答不知道。
4. 对话和表单形成同一份结构化草稿，明确展示与旧版的差异。确认角色与确认访问授权分开，未填的允许来源保持未声明。
5. 用户可接受、修改、拒绝或保留未知；确认后只保存本系统的画像／业务要求版本，不回写云端标签、分组或策略。
6. 已确认信息遇到新线索冲突时要求复核，不静默覆盖。旧审计绑定原版本，补充信息后通过新任务／复审生效。

| 画像信息 | 最小内容与约束 |
| --- | --- |
| 角色与服务 | Web、数据库、后台服务、管理入口、未知；同机可有多角色并关联服务 |
| 应用、环境和重要性 | 有则自动显示或人工补充，缺失保持未知，不按名称猜重要性 |
| 访问关系 | 明确调用方、服务、协议／端口与是否需公网；配置中允许的来源不能直接复制成业务授权 |
| 来源／状态／版本 | 自动事实、模型候选、人工／受信映射确认及冲突分别记录，保留确认时间、范围和版本 |
| 例外 | 对象、理由、授权来源与到期；确认本地例外不等于云端修改，也不删除原始风险事实 |

详细页面职责、正常／异常路径、报告和复审流程见 PRD 的 UF-01～UF-08。该流程已纳入B2并完成整体设计审核，候选仍不能替代具体业务授权。

### 2.4 三台虚拟机的人工示例

下表仅为需求讨论用的构造场景，不是当前账号数据。

| 资产 | 已确认角色及需求 | 系统可以提出的建议 | 不允许直接推断 |
| --- | --- | --- | --- |
| VM-A | 公网 Web 服务，明确需要 HTTPS；管理仅来自指定入口 | 核对 Web 必要访问、管理来源、CFW 覆盖；评估 Web 应用防护的适用性 | 不能据“Web”自动开放全部端口或认定一定没有 WAF |
| VM-B | 自建数据库，仅接受 VM-A 的应用服务访问，协议／端口已确认 | 检查面向公网的数据库暴露；建议限制到已声明调用方，并审查网络分层的必要性 | 可以因名称／安全组端口提出候选，但未经确认不作为最终角色；不假定其公网访问已获批准 |
| VM-C | 角色未知；可能是后台服务，也可能兼有 Web 与数据库 | 先做不依赖角色的基线检查，针对影响建议的问题请求补充角色或访问要求 | 不默认 Web，也不因无标签而停止所有审计或给出宽泛放行建议 |

角色识别不是复杂算法前提。最小可用方案是少量人工标注和显式访问关系；无需额外安全产品即可自动取得的元数据／安全组线索可以先用，日志仍为受限可选增强。

## 3. 防护组件建议的分层原则

组件建议用于回答“需要检查哪一层防护、适用条件是什么”，不是要求每个资产购买全部产品。必须区分 **适用性建议、已证实配置缺口、未知待核查**；未读取某产品状态不能写“未部署”。

| 防护层／组件 | 适用条件与参考 | 基础建议 | 本项目边界 |
| --- | --- | --- | --- |
| 网络访问控制／安全组 | 所选云主机，NIST 与厂商最小暴露原则（B-01、B-03、B-04） | 核对必要服务、可信来源、管理入口及例外；拒绝路径需与必要访问配套 | 不执行安全组写入，不承诺完整端到端证明 |
| CFW 互联网边界保护 | 拟纳入保护的公网资产（A-17） | 核对实际保护开关与范围，再审查 ACL；明确未保护时优先处理该层缺口 | 关闭不等于“从未防护”或“没有任何防护” |
| 入侵防御 | 在相应产品／链路适用且已声明保护目标时（A-18） | 核对检测与拦截预期；观察模式已有检测作用，升级拦截前评估误拦截 | 首版可输出核查清单；精确状态检查需快照／人工证据或后续适配 |
| 日志与审计 | 被采用基线要求保留相应证据（B-01 §5.2.3、A-19、A-20） | 核对类型、范围、保存与可查询性；日志缺口不等于没有攻击 | 不默认统一天数或费用；直接 SLS 联接不作为首版默认交付 |
| Web 应用防护／WAF | 已确认的公网 HTTP/HTTPS 服务（A-25） | 评估应用层防护和入口部署位置，核对是否已被现有网关／WAF 覆盖 | 不给数据库套用 WAF，不在未核实状态时判定产品缺失 |
| 数据库访问分层 | 数据库角色、服务与调用关系已经确认 | 核对应用来源、管理入口和隔离需求，不给数据库统一套用 Web 防护 | 不引入云安全中心或数据库全栈审计，不承诺完整拓扑 |

DDoS 等能力仅在明确的公网服务风险、现有覆盖和业务要求下给条件评估，不形成“所有资产必须购买某套餐”的规则。产品版本、适用范围与可能费用均须核实，启用、升级及采购由人决定。

## 4. 采用范围

画像、条件化组件建议和核心基线已纳入B2并完成整体设计审核；角色不等于授权、配置端口不证明监听／可达性，不接云安全中心。新增基线、真实业务允许集合和可选M1仍按各自边界处理。
