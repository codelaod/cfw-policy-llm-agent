# 安全基线与规则目录

基线：需求v0.6／B2、设计v0.6，G1／G2已通过。本文为规则需求与判据目录；实际运行验收另行取证。

## 1. 依据分层：什么由代码判，什么由模型解释

| 依据层 | 来源与用途 | 允许的结论 | 不允许的迁移 |
| --- | --- | --- | --- |
| 产品事实 | CFW 用户手册、查询字段、日志字典（A-02／03／05／08／17～20） | 在已支持条件下还原配置和证据含义 | 不能把默认放行按默认拒绝计算，不能混用 ACL 与 IPS 日志标识 |
| 权威原则 | NIST SP 800-41 Rev.1 §4、§5.2.3（B-01），资源中心视角参考 SP 800-207（B-02） | 支持最小必要访问、策略维护和日志审计等原则 | 不是本账号的认证证书，也不给出本项目自行设定的统一端口／天数阈值 |
| 厂商控制／最佳实践 | AWS EC2.13／14／18／19、阿里云 ECS 最佳实践／安全组检查（B-03、B-04、A-22） | 为高风险公网开放等检查主题提供依据 | AWS 安全组判据不能原样用于阿里云 CFW；厂商阈值不自动成为通用强制规范 |
| 项目安全基线 | 用户审核后选用的端口风险表、防护要求和例外 | 即使业务白名单缺失，也能判断是否违反已采用的基线 | 未审核的默认建议不能当成用户已经接受的安全政策 |
| 业务访问要求 | 已确认角色、调用关系、允许集合、必要访问与例外 | 判断是否违反该业务的具体要求 | 名称、标签、安全组配置、模型猜测和历史访问不自动等于授权 |

项目将“合理”落实为可定位的业务与安全判据，将“合规”限制为**对明确选用条目的符合性检查**。没有指定规范／条目时称为安全基线或业务一致性，不输出“整体合规”“符合某监管要求”等结论。

代码执行已审核且可确定计算的条件；模型获取同一版本的规则说明、适用条件和证据，通过工具补查并解释结果。模型不得自行修改端口表、严重程度依据、例外或判据版本；其新增疑点单独标记，不能当作确定性检查通过／失败。

模型使用的规则说明至少包含编号／版本、依据类型、适用前提、禁止推断和可用证据。推荐需引用对应规则／业务要求、目标资产与服务、证据、成立条件和影响；找不到依据时只能说明待确认或信息不足，不能生成不存在的规范条目。采用提示说明不等于让模型自行裁定全部合规，也不要求建设复杂知识库。

## 2. 规则契约与判定过程

每条规则须有：编号／版本、依据类型与来源、适用范围、输入字段、前提、支持／不支持条件、判定步骤、例外处理、严重程度依据、整改优先级、证据、推荐边界及正反／缺失案例。数据schema与算法见审计设计，本目录只定义规则需求。

统一判定顺序：确认规则适用 → 检查输入与语义是否可用 → 计算事实／差异 → 附加业务上下文和例外 → 生成证据及状态 → 校验推荐。没有相关规则也可能命中默认放行，不能以空策略列表直接判定未开放。

对有效允许／拒绝的推导，必须满足领域 DR-01：保护状态、相关规则、顺序、匹配条件、状态和默认行为足以判断；否则只保留配置事实，输出待确认／信息不足／不支持，不假装已证明运行时可达。

判定状态与严重程度独立：通过、不符合、待确认、信息不足、不适用、不支持；模型疑点另列。“未发现已确认问题”不等于全部检查通过。授权例外标明“已接受例外／待复核”，保留事实和到期，不静默删除问题。

## 3. 三类优先级不得混用

| 维度 | 拟定等级及含义 | 决定依据 |
| --- | --- | --- |
| 实现范围 | M0：已纳入 B2 的核心需求；M1：可选增强、默认关闭；M2：后续扩展 | 用户的交付选择，不表示安全风险大小；精确实现见已批准审计设计，尚未运行验收 |
| 风险严重程度 | 高／中／低／信息；没有充分证据不默认标严重 | 已证实的允许范围、攻击面、业务影响、可信防护与例外 |
| 整改顺序 | R1：优先处理；R2：计划整改；R3：优化复核；V0：先核实关键缺口 | 风险、业务重要性和证据充分度；不承诺未定义的时限 |

拟定排序原则：已确认的高风险公网访问或重要资产明确覆盖缺口优先；证据未知进入核实队列，不能因为未知被当作安全而沉底；重复配置和零命中候选通常后置。只按端口出现、模型置信度或产品数量不能提高严重程度。存在已有替代控制时保留证据，由已审核基线决定是否接受。

### 3.1 首批高风险端口基线主题

下表是 B-03 控制主题的**项目选取子集**，现有五个端口主题已作为 B2 基线目标采用，不是完整危险端口清单、服务探测结果或通用法定要求。具体规则契约、版本化与例外机制见已批准设计；新增条目及实际业务例外另行确认，不照搬 AWS 的全部默认参数或严重程度。

| 候选主题 | 协议／端口 | 项目判据使用方式 |
| --- | --- | --- |
| 远程管理 | TCP 22、3389 | 仅当宽泛来源条目／默认放行留下可证明的允许范围且不满足已采用基线／例外时产生 CHK-07；不是发现端口数字即判高危 |
| 关系数据库常见入口 | TCP 3306、5432、1433 | 可作为端口风险主题；实际数据库类型／端口仍需画像确认，CHK-08 使用真实服务端口而非强套默认值 |
| 其他／自定义端口 | 不自动补全 | 从已确认业务服务或另行核实的基线加入并评审；不因未在表中就称安全 |

整改顺序示例：已证实公网管理／数据库超范围且无例外通常 R1；仅证实 CFW 关闭但其他层未知通常 R2 并核对覆盖；关键资产的未知状态先进入 V0；精确重复和零命中候选通常 R3。必要访问和生效路径未核清前，不直接添加全局拒绝或开启拦截。

## 4. 核心与可选规则的需求细化

### CHK-01 管理来源与明确要求不一致（M0，业务一致性）

- 依据：B-01 §4、已确认管理访问要求；涉及 CFW 语义参照 A-03／08。
- 输入／前提：管理服务及端口、完整的允许来源、例外、相关完整可支持配置。
- 判据：计算该管理服务的有效允许来源与业务允许集合之差；存在非空差异则不符合。缺少业务允许集合时不运行本项确定性业务比较，转待确认；仍可独立运行 CHK-07 基线。
- 输出／建议：差异范围、业务要求版本和相关规则；建议限制到真实声明来源并检查兜底。已确认显著超范围通常高、R1；不能自行生成白名单或把单条缩小当成已阻断其余来源。

### CHK-02 非预期协议／端口放行（M0，业务一致性）

- 依据：B-01 §4、业务完整允许集合；B-03 EC2.18 仅作为主题参考。
- 输入／前提：适用资产、协议／端口允许集合的完整性、所审流量范围与相关配置。
- 判据：支持范围内的有效允许协议／端口超出明确允许集合。非完整列表不能证明其余端口违规；协议 ANY 不得只按 TCP 处理。
- 输出／建议：具体差异与受影响访问，按服务风险和业务影响定级，R1 或 R2；推荐不得删除明确的必要服务。

### CHK-03 业务服务来源超范围（M0，业务一致性）

- 依据：B-01 §4、该服务的明确允许来源。
- 输入／前提：具体服务与完整允许来源，地址引用完整展开且相关策略语义可判。
- 判据：有效来源集合超出该服务的授权集合；未知引用不按空集合计算。
- 输出／建议：来源差异、引用与策略证据，按服务影响定级；与 CHK-01 同一问题关联展示，实验不重复计分。

### CHK-04 精确重复配置候选（M0，配置维护）

- 依据：B-01 的策略维护原则；“精确重复”的操作定义由本项目给出。
- 输入／前提：两条规则所有影响匹配、生效和动作的条件完整可比较。
- 判据：在所支持语义下相同，仅标记冗余候选；未知条件不能被删除后宣称等价。
- 输出／建议：成对字段比较与位置，通常低、R3；人工复核业务、位置与其他依赖，不自动删除，不将重复数等同漏洞数。

### CHK-05 当前 CFW 防护覆盖缺口（M0，安全基线／明确保护要求）

- 依据：A-17、A-02、用户选用的公网保护基线或资产保护要求。
- 输入／前提：资产身份、公网／保护适用范围、可信开关或保护状态、采集时间；可接受有来源的人工状态快照。
- 判据：资产适用且明确应受保护，而当前对应 CFW 状态明确关闭／未保护。切换中单列状态，未知进入 V0；若配置与数据面覆盖关系不足则不得给有效保护结论。
- 输出／建议：首先核对范围与接入，再安排该层保护，不直接给“购买全部组件”建议。默认中，重要性／高风险暴露经确认时可提高并排入 R1；单独关闭通常 R2。
- 边界：只能说“当前该层未保护”，不能说“从未被防护”“没有任何防护”；安全组、WAF、主机安全等其他层未知不等于不存在。

### CHK-06 明确必要访问被本层拒绝（M0，业务一致性）

- 依据：已确认必要访问、A-03／08。
- 输入／前提：必要访问范围、足以判断的有效配置；角色本身不能替代访问要求。
- 判据：在支持范围内存在必要流量被该 CFW ACL 拒绝。
- 输出／建议：拒绝范围与命中规则，按已确认业务影响分级，通常 R1 或 R2；只建议复核该冲突，不据此证明实际故障或自动放行。模型不得扩宽到未经批准来源。

### CHK-07 高风险端口宽泛来源放行（M0，选用的安全基线）

- 依据：B-03 EC2.13／14／19、A-22、B-04；判据按阿里云 CFW 语义重新定义。
- 输入／前提：版本化的高风险端口／服务表、所审公网访问范围、足以判断的配置及基线例外。
- 判据：默认基线候选先覆盖 SSH 22、RDP 3389 等管理入口；数据库／缓存默认端口另列风险主题，不能以端口证明实际服务类型。在所审端点／协议／端口上，存在由全地址来源条目（例如 0.0.0.0/0）或未命中默认放行形成的配置允许范围，且无有效例外，则不符合；若已知前置拒绝全部覆盖则不成立。只证明明确的放行范围，不声称全部公网或真实数据面可达，也不等同“其他端口安全”。
- 输出／建议：服务／端口表版本、有效公开范围、策略证据及例外；已确认的高风险公开通常高、R1。缺少业务白名单仍可给本项基线发现，但具体整改来源需确认；不把风险端口出现在任意位置就判高危。
- 边界：未知 CFW 状态／相关高级条件可能使有效性无法判定，此时保留配置候选；不移植 AWS 安全组的隐式拒绝语义。例外不代表没有风险。

### CHK-08 数据库角色与公网访问方式不一致（M0，角色基线＋业务要求）

- 依据：B-01 §4、B-04、用户采用的数据库角色模板；模板是项目政策，不是通用强制规范。
- 输入／前提：已确认数据库服务及实际端口、预期私有／限定调用关系、当前可判定的公网访问配置。可据普通 db 标签、关联安全组端口及模型建议形成候选，再由用户确认；候选不足以直接作为已确认角色。
- 判据：数据库已确认无需公网访问，却在支持范围内有效允许公网访问；若角色已确认但访问要求未知，只给模板核查／待确认，不伪造业务违规。
- 输出／建议：定位服务而非整机统一封锁；建议核对已声明应用来源、管理入口和隔离需求。经确认违规通常高、R1；兼有 Web 的同机资产不得一并关闭 Web 必要访问。与 CHK-07 重合时关联同一问题。

### CHK-09 入侵防御状态与保护目标不符（M1，防护配置）

- 依据：A-18 及已采用的检测／拦截目标。
- 输入／前提：相关资产／链路、IPS 启用与模式证据、版本／适用范围、批准的保护目标与例外；读取路径未确定前只使用明确的人工或离线快照。
- 判据：明确要求启用检测而证实关闭，或明确要求拦截而仅处于观察；后者表述为拦截目标未满足，不说“没有任何防护”。状态未知则核查，不判缺失。
- 输出／建议：中、R2 为初始建议，结合已确认威胁证据再评估；从观察转拦截前分析误拦截、业务验证和回退，不自动开启或扩大到全部规则。

### CHK-10 日志审计要求未满足（M1，可观测性）

- 依据：B-01 §5.2.3、A-19／20 和已选日志要求。
- 输入／前提：明确需要的日志类型、资产／链路范围、窗口、保存／可查询要求以及实际开关和覆盖证据。
- 判据：已知关闭、明确缺少必需类型或明确不满足选定保存要求。只有空日志文件或查询零结果，无法证明日志未开启或无需审计；没有规定时不编造统一天数。
- 输出／建议：指出具体证据缺口，通常中、R2；说明产品／保存配置与潜在费用需核实，不自动开通日志服务或购买容量。

### CHK-11 观察窗口内零命中策略复核（M1，维护候选）

- 依据：B-01 的维护原则、I-02 的使用分析方向、A-19。
- 输入／前提：窗口 W 的起止时间由本次任务声明；相关日志类型、资产、规则版本、采集持续性、过滤／采样和标识映射可核实。无最低统一天数；窗口不足只能说明观察有限。
- 判据：在可核实窗口内未观察到该策略命中，仅生成复核候选；日志缺失、采集漏段或规则创建晚于窗口时，降级为信息不足。业务低频／备用／灾备访问必须纳入人工复核。
- 输出／建议：信息或低、R3；报告窗口与覆盖限制，不自动删规则，不称为无效或无用，不将其计为确定性漏洞。

### CHK-12 已声明必要访问的拒绝日志线索（M1，日志辅助复核）

- 依据：A-19、已确认且在日志发生时适用的访问要求。
- 输入／前提：来源／目标、时间、协议／端口、动作及可解释的 ACL 关联；考虑代理／NAT 位置、访问要求和策略的时间版本。
- 判据：可信拒绝记录与明确必要访问相符时生成调查线索；规则、业务要求或映射无法时间对齐时不判业务违规。历史访问本身不能证明其合法，威胁检测记录也不能直接当 ACL 拒绝。
- 输出／建议：待确认及 R1／R2 调查顺序取决于已确认业务影响；请求补充故障背景或规则证据，不因为拒绝日志而直接放行。不能据一条日志宣称业务已中断或主机已失陷。

## 5. 防护组件与日志的证据边界

官方当前手册区分日志审计与日志分析：前者可查看最近 7 天，原始日志导出或更长保存需后者（A-20）；A-19 字段字典针对日志分析数据。能在控制台查看日志，不等于已有原始导出／SLS 查询权限。M1 首先允许带来源的人工摘要，实际导入能力与完整性另核实；不把 7 天变成本项目统一阈值。

- 分层组件适用性见 [资产画像方案第 3 节](business-context.md)。M0 可输出“核查／评估”建议，但只有证实且违反已选目标的状态才形成配置缺口；不读取所有产品 API。
- 日志输入先建议离线／人工导出的受限摘要；原始数据保留在忽略目录，外部模型只接收获准范围内最小必要证据。未经授权不发真实日志。
- 摘要保留日志类别、事件时间、查询条件、记录数量的定义、范围／采样／缺段、策略／资产关联和字段映射版本。重复记录／流记录数不能随意称独立连接数或攻击次数。
- 按 A-19 区分 ACL 策略关联字段与 IPS 规则字段，保留未匹配／未知含义；不能仅因均叫 rule id 就关联。导出有日志不等于窗口全量，完整性无法核实时必须降级。
- ECS 元数据、安全组线索与日志可提高上下文充分度，但不能越过角色／授权确认；公开样例必须构造或脱敏，并记录其真实来源类型。

## 6. 新增验收案例与需求追溯

## 7. CR-1 出向／NAT 检查需求（B2已确认）

不机械地把入向规则“反过来”，也不为了增加规则数量扩展威胁情报／全量日志。以下命名只是评审标识；范围已由 [B2 需求确认](system.md) 采用；精确契约与优先级见已批准的规则设计。

| 候选 | 判定前提与结果 | 推荐边界 |
| --- | --- | --- |
| OUT-01 出向目标范围与明确要求的差异 | 资产与外部目标关系、允许集合及完整性已确认；本层有效允许范围计算完整。无业务声明时只给待确认，不判确定性违规 | 先收集真实依赖与例外，不生成虚构域名／IP 白名单 |
| OUT-02 明确必要外联被本层拒绝 | 必要访问已确认，规则／默认行为与范围完整，能证明该访问在本层被拒绝 | 只报告本层配置差异，不推导实际服务不可达 |
| NAT-01 NAT ACL 关联与证据完整性 | 核对防火墙、网关、资产和观察点；不足时输出信息不足，而不是风险通过或未部署 | 补证据后再判断，不推定 SNAT／DNAT 映射 |
| NAT-02 NAT 本层规则一致性 | 在同一 NAT 防火墙／网关中，完整受支持语义下复用明确需求比较、精确重复和覆盖状态检查；适用前提逐项复核 | 不沿用互联网的未核实默认值，不跨规则集排序，不套用入向高风险端口基线到出向目标 |

原型的 OUT-01／NAT-01 是固定人工结论；不是规则实现、单元测试标签或业务效果证据。本次范围采用来自用户明确需求确认，不因原型有入口就认定实现或效果已通过。
