## 3. 实施顺序与阶段产物

| 阶段 | 主要工作 | 完成标志 |
| --- | --- | --- |
| P0 目标与范围 | 确认边界、业务场景、检查项方向和论文主线 | 需求范围可用于开题 |
| P1 最小技术验证 | 验证云端只读接口、分页与字段；验证模型多轮工具调用 | 有少量可复用样例和能力核实记录 |
| P2 方案定稿 | 决定技术栈、Agent 实现方式、数据模型、接口与页面 | 架构与实施方案可评审 |
| P3 业务基础 | 离线数据、归一化、业务意图、规则引擎与报告 | 离线规则审计闭环可运行 |
| P4 Agent 与 Web | 工具循环、证据、推荐、前后端页面与错误反馈 | 从 Web 发起并审阅完整审计 |
| P5 实验与云端演示 | 固定案例、运行对照实验、人工修改与复审 | 有可复核结果、截图与费用记录 |
| P6 论文整理 | 整理设计、实现、评估及局限，核对文字与代码一致 | 论文和答辩材料完整 |

开题报告可在 P0～P2 同步推进，实验结论须待 P5 产生。尚无明确截止时间，暂不编造逐周排期。

## 4. 下一轮优先讨论

先讨论首个审计边界、演示业务需求以及如何证明 Agent 对审计有帮助，再讨论框架。可按以下顺序推进：

1. 用一个“公网 Web 服务 + 受限管理访问”的业务案例确认资产、策略和预期行为。
2. 从案例推导首批检查项与信息缺口，核实阿里云字段能否覆盖。
3. 画出规则扫描、固定模型流程和 Agent 补查的差异，确定实验比较方式。
4. 结合开发习惯选择前后端与 Agent 实现方案，形成开题所需技术路线。

## 5. 变更约定

已确认决策变更时记录理由，并同步范围、架构和实验设计。保持“规划中、已实现、已验证”三种状态可区分；后续不为追求技术数量而扩展多云、多 Agent、自动下发和复杂知识库。
