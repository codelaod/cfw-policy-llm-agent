## DFX检查范围

质量检查限定为可用、可恢复、可诊断、可测试、可维护和安全，纳入正常业务联调，不新增复杂技术栈或专项基础设施。下表是验证要求，不是已完成测试或外部评审结论。

| 方面 | 发现／处置 | 实现时怎么查 |
| --- | --- | --- |
| 并发与体验 | 原全局单工作器不满足最低体验，已改为3槽位；SQLite使用常规WAL池 | 3会话真实重叠、同会话不重复、第4个有清楚排队 |
| 数据与取消隔离 | 并发后不能共享可变Runner／消息／scope，也不能取消其他会话 | 交叉输入／工具／报告和单任务取消验证 |
| 正确性与费用 | 并发不扩大云权限或总预算；输入／审阅版本与事件保持一致 | 原有幂等／修订冲突和共享最后一次预算竞争 |
| 失败与恢复 | 外部失败保留规则；存储失败不显示已保存；重启不重放模型／云 | 局部失败、保存失败、重启后历史与interrupted记录 |
| 可诊断性 | request_id／job_id／attempt_id能关联，区分排队、实际执行和订阅状态 | 简单结构化日志和受保护的本地状态，启动／健康不外呼；不建监控集群 |
| 维护与交付 | 接口生成并保留；依赖固定；私有数据可备份恢复 | 正常构建、路由／文档检查和一次本地备份恢复；不设SQLite专项框架 |
| 安全与范围 | 凭据不进模型／前端／文档／报告；保持只读和既定产品边界 | 既有访问／scope／脱敏检查；不增加身份平台或云写 |

备份采用简单可靠的停机一致复制，包含数据库和被引用的原文／快照；不要只拷运行中的主DB而丢掉WAL状态（D6-01／03）。恢复先在独立私有目录核对，不覆盖当前数据、不自动重跑任务。磁盘／数据库不可写时停止新外呼并明确错误，不能虚报终态已持久。不要为此新增在线备份服务、监控平台或自研存储协调。

普通停机停止新任务、尽力结束／中断活跃执行；再次启动沿用独占实例检查和持久记录恢复。这里落实已有恢复需求，不新增RPO／RTO或硬件零丢失保证。
