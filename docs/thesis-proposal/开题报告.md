# 开题报告

**论文题目：基于大模型智能体的云防火墙策略审计与推荐系统设计与实现**

## 选题背景与意义

在云上业务的日常运维中，访问控制策略会随应用上线、联调测试和故障排查不断调整。临时放开的管理端口可能在问题处理结束后仍保留原有规则，业务迁移或资产用途改变后，原有访问范围也可能不再适用。运维人员需要结合当前业务要求，持续核对云防火墙策略是否适当。

策略审计需要同时理解配置语义和业务要求。公共 Web 服务与内部数据库的访问约束不同，多条规则的匹配范围、动作、执行顺序和默认行为又共同决定配置效果。近期研究通过原子谓词表达规则匹配空间，开展异常分析与处理[1]，为确定性检查提供了方法基础。人工审计还需在资产信息、策略列表和业务说明之间反复核对，判断访问授权与修改影响。将可重复的配置计算与必要的上下文获取结合，形成有证据支撑的建议，是本研究关注的工程问题。

英国国家网络安全中心的评估指出，人工智能既可被攻击者用于辅助漏洞研究与利用代码开发，也可帮助防御方改进系统安全。面向策略审计，大模型智能体可通过工具交互补充分析所需的信息：ReAct 依据环境反馈组织后续行动[2]，Toolformer 研究模型学习使用外部工具的方法[3]；网络配置分析研究进一步结合大模型、知识图谱与形式化工具开展配置解析和分析[4]。模型也可能遗漏业务条件，外部工具内容还会带来间接提示注入风险[5]，因此需要将证据获取、工具权限与执行约束一并设计。

本研究拟设计并实现面向公有云云防火墙的策略审计与推荐系统，贯通数据准备、业务确认、策略检查、建议审阅和整改复审。确定性规则负责配置语义检查，受限智能体按需调用只读工具补查证据、解释风险并提出条件化建议。策略由操作人员审阅后手动应用，系统通过重新采集和再次审计复核整改结果，并以统一数据模型、证据引用和连续历史记录保存判断依据。

将配置问题、业务依据和修改影响集中呈现，有助于减少重复核对，支持安全人力有限的团队持续开展审计。清晰的证据和人工审阅有助于控制不当整改对正常业务的影响。研究通过可解释的策略检查、受限证据补查与整改复审，探索大模型在安全运维中的应用方式，为提升安全运维效率、保护数据与个人信息、维护业务连续性提供工程实践参考。

## 论文综述（综述国内外有关选题的研究动态）

### 国外研究现状

防火墙策略分析的重要思路之一，是将规则的匹配空间和处理动作转化为可计算的关系。Bringhenti 等采用原子谓词分解匹配空间，分析包过滤策略中的异常并研究相应处理方法[1]；其另一项研究面向虚拟网络，在给定网络和安全要求的条件下，使用 MaxSMT 求解防火墙配置[6]。两项工作分别面向既有规则的异常识别和满足约束的配置生成，体现了配置建模与明确安全要求在自动化策略处理中的作用。

模型如何获取和利用外部信息，是工具增强智能体研究的核心问题。ReAct 将任务分析与行动交替组织，使模型能够根据环境反馈调整后续步骤[2]。Toolformer 通过自监督学习，使模型学习何时调用外部 API、传入哪些参数以及如何利用返回结果[3]。前者侧重交互执行过程，后者侧重工具使用能力的学习，分别从应用流程和模型训练层面探索语言模型与外部工具的结合。

在具体安全任务中，多步骤执行和上下文保持是智能体工程的重要内容。PentestGPT 围绕渗透测试组织大模型任务流程，通过模块分工组织任务分析与上下文管理，并结合测试任务评价其表现[7]。该研究将评价对象从单次回答扩展到任务推进过程，为安全智能体的流程组织和过程评价提供了参考。

工具集成同时引入了新的安全问题。InjecAgent 构建间接提示注入评测，研究攻击者通过外部工具内容影响智能体行为的风险[5]。这一方向将工具返回内容的信任边界纳入智能体安全评价，为应用侧的对象授权、参数校验和外部内容隔离提供了依据。

### 国内研究现状

国内关于网络配置正确性的研究，从不同层次梳理了验证对象与分析方法。方星等将相关工作划分为数据平面、控制平面和有状态网络验证，讨论各类技术的问题与适用范围[8]。在防火墙策略工具方面，赖清楠提出的 AT4FP 结合区间树与状态图开展异常检测[9]。网络验证研究提供了配置分析的分类框架，具体检测工具则将规则表达、异常识别和结果组织连接起来。

策略配置研究也关注运行信息的利用。李沛婷等结合流量分析、特征库与策略分析，研究防火墙安全策略的配置和优化建议[10]。流量辅助方法着重从观测访问中提取策略线索，配置审计则通过规则语义和业务访问要求建立判断依据，两类方法在输入来源和分析目标上有所区别。

在大模型工具使用与智能体构建方面，郭先会等梳理了智能体构建方法及有效性评估[11]；林衍凯讨论工具学习中的意图理解、规划、工具使用和记忆管理等环节[12]；郑逸宁等总结大语言模型工具使用的概念、技术方法与数据集[13]。这些研究将工具使用置于任务理解、规划、执行与评价的整体过程中，为分析智能体的能力组成和工程职责提供了技术框架。

大模型的网络应用包括配置生成与配置分析。杨兴源等面向 SDN 网络，在数据平面采用检索增强生成 P4 代码，在控制平面通过任务分解生成流表配置[14]。李鹏飞等利用知识图谱组织配置与网络状态信息，结合 ReAct 和形式化工具开展配置错误检测等分析[4]。两项工作分别围绕新配置生成和既有配置分析展开，其输入形式、处理流程与评价对象体现了不同任务的特点。

在相邻的运维分析场景中，康俊驰等从信息获取、根因定位和效果评估三个阶段梳理大语言模型智能体的应用[15]。该研究以软件系统故障定位为目标，将信息获取、分析过程和评价结果联系起来，为运维智能体的任务组织提供了参考。

### 研究现状评述

现有研究围绕规则异常分析、约束驱动的配置生成、工具增强交互和大模型辅助网络分析形成了多条技术路线。确定性方法通过明确的配置模型和安全要求计算策略关系，智能体方法通过外部工具获取信息并组织多步骤任务。两类方法在配置审计中具有互补作用：前者提供可重复的检查结果，后者支持上下文获取、业务解释和建议生成。

云防火墙审计涉及配置采集、业务说明与整改复核之间的信息关联。配置事实描述规则的匹配与处理关系，业务要求提供资产职责和访问授权，两者共同构成风险判断的依据。基线检查依据选用的安全要求识别配置风险，业务一致性检查依据用户确认的访问要求核对策略。证据充分性评价识别业务资料和采集数据中的缺项，为信息补充和结论适用范围的确定提供依据。

研究围绕上述关联关系构建审计与推荐流程，以统一数据模型衔接只读采集、业务确认、确定性检查、智能体证据补查、推荐审阅和人工整改后复审。规则发现与模型推断分别保存，工具事件摘要和证据引用用于说明分析过程。通过规则、固定模型流程与智能体工具选择的对照实验，评价推荐质量、证据利用和执行开销，分析动态补查在策略审计中的作用。

## 系统相关技术分析说明

系统采用策略语义分析、智能体工具调用、Web 交互和关系数据持久化等技术，通过统一数据模型与应用服务连接各部分。以下说明相关技术的基本原理、采用理由及其在审计流程中的作用。

### 云防火墙策略与访问控制语义

云防火墙通过访问控制规则约束所保护边界的网络流量。策略语义由方向、协议、地址与端口范围、处理动作、执行顺序、启用状态、引用对象及默认行为共同构成。地址和端口范围可表示为集合或区间，用于计算规则包含、相交及访问范围差异；原子谓词分析进一步体现了匹配空间建模在异常识别中的作用[1]。

规则引擎按照确定的语义子集计算策略关系，并在结果中列明分析覆盖的条件。应用、域名和识别模式等条件纳入语义覆盖检查，覆盖缺口作为审计依据的一部分单独说明。系统的分析对象为配置层访问关系，业务授权依据由用户确认的访问要求提供。

### 大模型工具调用与 ReAct 智能体

工具调用将模型生成的结构化请求交给应用执行，再把工具结果返回模型。ReAct 通过任务分析与行动的交替组织，使后续工具选择能够依据中间反馈调整[2]。系统将资产、策略、业务要求和证据查询封装为只读工具，由智能体根据分析目标逐步补充上下文。

工具执行受参数、对象范围和调用预算约束，工具结果作为分析数据处理，并与执行指令隔离，以控制间接提示注入风险[5]。输出区分规则发现、模型推断和业务信息补充项，配置建议列明修改对象、证据、适用条件与业务影响。

### Eino 智能体编排与 Go Web 服务

Go 后端负责数据接入、领域计算和应用服务；Gin 提供 HTTP 路由、JSON 请求处理及中间件，承担 Web 接口入口。Eino 组织模型与工具之间的交互循环，审计规则、证据关联、工具授权和业务状态由应用服务管理。这一分工保持后端技术栈的一致性，并将接口处理、领域计算与智能体执行分离。

HTTP 接口完成请求校验与任务提交，审计工作器执行云查询、规则计算和模型调用。业务会话存储与框架执行上下文分别管理，会话、任务和报告通过应用数据层关联保存。耗时调用采用超时和预算控制，并在数据库事务之外执行。

### Vue 与 TypeScript 前端开发

Vue 通过组件化与响应式机制组织资产表格、业务表单、任务状态、证据详情和推荐审阅等界面。TypeScript 对前端数据对象和接口使用进行静态类型检查，Vite 提供开发服务与静态资源构建。在前后端分离的结构中，前端负责数据呈现和交互，服务端负责运行时输入校验、权限控制和业务版本管理，云与模型凭据由后端保存。

### SQLite 数据存储与事务管理

SQLite 是嵌入式关系数据库，无需独立数据库服务，适合单机部署下的业务记录持久化。系统通过纯 Go 驱动管理业务要求版本、连续会话、任务和报告等关联数据。云配置通过只读接口采集，业务确认、消息保存与任务创建通过本地数据库写入记录。

事务将相关操作作为整体提交，并在失败时回滚。例如，业务要求确认将版本核对、版本创建和草稿状态更新纳入同一事务；消息发送则统一提交消息、轮次、幂等记录和任务记录。数据库采用单连接与短事务，事务覆盖必要的本地读写，云接口、模型请求和耗时计算在事务外执行，以保证关联数据的一致性并控制连接占用时间。

## 系统需求分析

系统面向运维与安全审计人员，围绕数据准备、业务确认、审计推荐和人工复审形成连续流程，主要需求如下。

（1）云平台接入与审计范围。系统面向公有云云防火墙建立统一审计输入，以阿里云云防火墙及 ECS 作为接口适配和实验环境。在授权的账号、地域和资源范围内，只读采集资产、防护状态、访问控制策略及必要的安全组上下文，同时支持离线快照导入。采集结果记录来源、时间、分页状态和错误原因，区分无配置、读取失败与数据不完整等情况。

（2）运行环境与模型接入。系统采用单机 Web 运行方式，云与模型连接通过显式配置管理，凭据保存在后端，数据库使用纯 Go 驱动。模型接口支持多轮工具调用、工具结果关联、结构化输出和异常响应，满足连续审计任务的执行要求。

（3）用户与业务流程。操作人员依次完成配置查看、资产画像与业务要求确认、审计发起、证据核对和建议审阅。资产职责和访问授权分别记录，自动提取的配置特征用于辅助业务信息整理。审阅意见在本地保存，云上策略由操作人员手动修改，整改效果通过重新采集配置和执行审计进行复核。

（4）系统功能与结果交付。系统提供资产和策略审阅、画像与业务要求管理、规则检查、智能体补查、配置建议和报告复审功能，核对过宽放行及必要访问的配置差异。规则发现与模型推断分别呈现，建议列明对象、适用条件、证据和影响。任务执行中的规则结果与证据独立保存，支持报告阅读和结构化结果导出。

（5）数据与连续历史管理。系统支持固定快照、符合完整性与时效要求的数据复用以及主动刷新，保存各数据族的采集时间和版本。业务要求实行版本化管理，分别保存编辑稿和用户确认记录；会话、用户可见消息、任务、工具事件及报告关联持久化。审计任务绑定数据、业务和规则版本，历史结论保留原始依据，模型交互记录保存工具事件摘要与结果。

（6）安全与运行质量。系统对本地接口实施访问控制和输入校验，对工具实施只读白名单、对象校验以及轮次、总时限和调用量控制。模型输入使用授权范围内的字段集合。界面呈现排队、采集、分析和报告生成等阶段的状态、错误与耗时。历史消息读取与任务执行分离，外部调用由明确的任务操作和授权策略触发。

## 研究内容与方法

### 研究内容

研究围绕云上运维与安全审计中的两个问题展开：一是云配置、业务要求与检查依据的关联表达，二是动态证据补查对推荐质量和执行开销的影响。具体包括以下五方面。

（1）云防火墙审计数据的建模与管理。建立策略、资产、防护状态和业务访问要求之间的关联，将只读采集与离线快照转换为统一输入，记录来源、采集时间、完整性和版本。通过阿里云相关接口实现适配，接口与字段差异由适配层处理。资产职责与业务访问要求经过用户确认后保存，审计任务绑定配置快照和业务版本，形成历史结论的追溯依据。

（2）基于策略语义的确定性审计。依据产品语义开展安全基线检查与业务一致性检查，重点分析防护覆盖、过宽访问及规则重复关系。判据考虑方向、协议、地址与端口范围、动作、顺序、状态、引用及默认行为。规则发现独立保存，附带证据、语义覆盖范围和采集完整性说明。

（3）受限智能体的证据补查与条件化推荐。设计资产上下文、策略详情、业务要求和证据查询等只读工具，由智能体根据工具反馈选择补查路径。业务资料存在缺项时，通过对话或表单收集补充信息；涉及业务授权的建议以用户确认的访问要求为依据。配置建议说明修改对象、证据、成立条件与业务影响。模型推断与规则发现分别记录，工具执行受参数、对象范围和调用预算控制。

（4）审计与推荐系统的设计实现。采用前后端分离的 Web 结构，实现数据准备、业务确认、审计执行、建议审阅和报告生成。后端统一管理云与模型凭据，持久化连续会话、确认记录、任务、工具事件摘要与报告。系统以人工应用策略、重新采集与再次审计连接整改和复审流程。

（5）系统测试与协同效果评价。设计正常配置、风险配置、业务例外和数据不完整等案例，开展功能、策略语义、异常处理、安全和性能测试。对比仅规则、规则＋固定模型流程、规则＋智能体工具选择三种方式，分别评价规则识别、模型分析和建议质量，并统计调用次数与端到端耗时，通过云环境实验检验数据采集和整改复审流程。

预期成果包括 Web 审计与推荐系统、统一审计数据模型、规则目录、标注案例集、带证据的审计报告及对照实验分析。

### 研究方法

（1）文献研究与需求分析法。梳理防火墙规则分析、网络配置验证、工具调用和智能体安全研究，结合审计场景分析使用者、输入输出与业务流程，形成数据管理、策略判据、业务确认和运行质量需求。

（2）策略语义建模与案例分析法。使用统一对象表达策略及其匹配条件，通过地址、端口和规则关系计算建立确定性判据。构造正常、冲突、业务例外及数据不完整案例，分析判据、证据和配置建议之间的对应关系，并分别表达配置事实与业务授权。

（3）系统设计与迭代实现法。采用模块化方式划分云平台适配、数据归一化、规则审计、智能体编排和 Web 交互，设计持久化实体、接口及权限控制，通过交互原型、模块实现和集成测试完成系统功能。

（4）对照实验与测试验证法。设置仅规则、规则＋固定模型流程、规则＋智能体工具选择三组实验。三组使用相同的数据快照、业务版本和规则结果；两个模型组在模型、采样参数、初始信息、可访问工具与调用预算上保持一致，分别采用预设补查流程和依据反馈选择工具的执行方式。调试案例与评价案例分开，评价前确定标签和问题匹配规则，采用具有前后依赖关系的补查任务分析证据获取与建议生成效果。通过少量代表案例的重复运行评价输出稳定性，独立案例数与重复运行次数分别统计，以任务完成率、失败率、调用次数和耗时描述执行表现。

评价方案设计20—30个人工构造案例，覆盖正常配置、风险配置、业务例外和数据不完整等情形，并标注目标问题、证据位置、业务信息缺项及建议要求。采用查准率、查全率和误报漏报计数评价规则识别效果，列出指标的原始计数与适用样本范围；数据不完整案例单独评价缺项识别和信息补充效果。规则发现、模型推断和配置建议分别评价，建议质量从对象准确性、证据支撑、业务约束一致性及授权范围四个方面进行人工评分，附以相应依据。云环境实验评价配置采集、资产关联和整改复审流程。

## 论文组织结构

全文围绕云防火墙审计业务和智能体工程两条主线展开，共分为七章，各章安排如下。

第1章为绪论。说明课题背景、研究意义及国内外研究现状，归纳需要解决的问题，明确研究内容、研究方法和论文整体安排。

第2章为系统相关技术分析说明。围绕审计任务，分析云防火墙策略语义、大模型工具调用与 ReAct 方法、Eino 与 Go Web 服务、Vue 与 TypeScript，以及 SQLite 数据存储与事务管理，说明相关技术的作用、采用理由与适用边界，为需求分析和系统设计提供技术依据。

第3章为系统需求分析。从云平台接入、运行环境、模型接口能力和用户使用流程出发，分析资产与策略管理、业务访问要求确认、审计推荐和报告复审需求，重点说明快照、业务版本、连续会话与历史记录的管理要求，以及安全、可靠性和性能约束。

第4章为系统设计。给出总体架构与模块职责，设计审计数据模型、策略归一化与规则检查、智能体工具调用及证据补查、条件化推荐与人工复审，并说明任务执行、连续会话、接口和安全控制。

第5章为系统实现。说明开发与运行环境，分别介绍只读采集与快照管理、资产画像与业务确认、确定性规则审计、智能体证据补查与推荐、连续会话与任务执行，以及 Web 交互、报告生成与人工整改后复审的实现，展示各模块如何贯通审计流程。

第6章为系统测试。说明测试环境、数据来源、案例标注和评价指标，开展功能、策略语义、证据正确性、异常处理、安全与性能测试；在共同的数据、业务版本和规则结果上对比三种方式，并固定两种模型方案的模型与预算条件，结合云环境演示与整改后复审分析适用范围和局限。

第7章为总结。总结研究工作和系统设计实现，结合测试、实验与使用流程归纳适用范围及不足，提出后续改进方向。
