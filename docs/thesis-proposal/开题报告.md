# 开题报告

**论文题目：基于大模型智能体的云防火墙策略审计与推荐系统设计与实现**

## 选题背景与意义

随着业务系统向公有云迁移，服务器、网络资源与访问控制策略逐步通过云平台集中管理。云防火墙承担云上网络边界的访问控制职责，但部署安全产品并不意味着配置始终符合业务要求。业务上线、资产用途调整和临时运维，都可能使规则与当前需求发生偏离。因此，安全管理不能止于“是否部署防火墙”，还需要检查“保护了哪些资产、允许了哪些访问、这些允许是否有依据”。

策略是否合理，取决于配置语义与业务背景的共同约束。同样的公网允许规则，对公共 Web 服务和内部数据库可能具有不同含义；管理端口是否应当开放，也取决于明确的运维来源。同时，多条规则的顺序、匹配范围、动作和默认行为共同决定配置层面的访问结果，不能仅凭单条规则判断整体效果。已有研究围绕规则冲突、遮蔽和冗余建立了分析方法[1]，但形成可供处置的结论，还需要关联资产职责、业务授权与数据完整性。

人工审计能够结合业务进行判断，却往往需要在资产信息、策略列表和业务说明之间反复核对。固定规则适合处理可确定计算的问题，但难以独立完成背景追问、证据选择和整改影响说明；直接让大模型根据配置文本作答，又可能遗漏条件或补造业务需求。因此，本课题关注的不是以模型替代全部判断，而是如何在确定性分析基础上，补充必要上下文并形成有依据的建议。

大模型智能体为此提供了实现路径。ReAct 交替组织任务分析、行动和环境反馈，使模型能够根据中间结果继续选择行动[2]；Toolformer 展示了模型学习使用外部工具的可能性[3]。在审计场景中，可将工具限定为资产查询、策略读取、引用展开和业务要求检索，让模型通过实际查询补充信息，而非仅凭文本推测。不过，工具内容也可能携带间接提示注入[4]，因此权限控制和执行边界应与智能体能力共同设计。

本课题以阿里云云防火墙与 ECS 为场景，构建覆盖数据准备、业务确认、策略审计、推荐审阅和修改后复审的 Web 系统。规则负责明确语义下的配置检查，智能体负责受限证据补查、业务解释与条件化推荐，由人确认并手动应用策略。通过统一数据模型、证据引用和连续历史记录，连接“发现问题”与“理解影响、复核整改”，并以对照实验分析规则与智能体协同的适用条件。

本课题的社会价值在于，将可解释、可复核的安全检查落实到日常云资源管理中。清晰的证据和整改影响说明，有助于降低运维人员理解复杂策略的门槛，减少因配置疏漏或不当整改引发的数据暴露与业务中断风险。对于缺少专职安全团队的中小组织，以适度复杂的工程方案辅助持续审计，有助于改善有限人力下的安全管理能力。同时，坚持最小权限、人工确认与结果留痕，也是探索生成式人工智能在安全运维中负责任使用的具体方式，最终服务于数据安全、业务连续性和数字服务可信运行。

## 论文综述（综述国内外有关选题的研究动态）

### 国外研究现状

国外防火墙策略分析研究较早关注规则之间的语义关系。Al-Shaer 等于 2005 年对分布式防火墙策略冲突进行分类与分析，将规则匹配范围、处理动作及配置关系转化为可分析的异常问题[1]。随着研究对象由规则集扩展至云网络配置，Backes 等于 2019 年提出面向 AWS 网络的可达性分析方法[5]，体现了以形式化模型验证云配置的研究方向。这些工作为本课题处理策略关系和配置层结论提供了基础，也提示审计必须明确输入范围与模型假设，不能把配置中的允许直接等同于实际服务可达。

2023 年，大模型与外部工具协同逐渐成为智能体研究的重要方向。ReAct 通过交替组织任务分析、行动和环境反馈，使模型能够根据中间查询结果继续选择行动[2]；Toolformer 则探索模型学习选择和调用外部工具的方法[3]。两者分别从交互式执行和工具使用学习角度说明，智能体的价值不应只通过一次文本生成体现。对于云防火墙审计，这一发展为“发现信息缺口—选择查询工具—利用返回证据—形成条件化建议”的流程提供了参考；本课题侧重应用层的工具编排与约束，不开展通用工具模型训练。

2024 年，相关研究进一步进入具体安全工作流程与智能体安全评估。PentestGPT 将大模型用于组织渗透测试过程，关注安全任务中的上下文保持和过程管理[6]，说明模型能力需要通过持续的任务流程与外部反馈落实。InjecAgent 则评测工具集成智能体面临的间接提示注入问题[4]，表明外部工具内容也可能影响模型行为。二者分别从安全应用和应用安全角度，为本课题的过程记录、证据利用、只读工具和权限校验提供了参考，但渗透测试与配置审计的任务目标和评价标准仍需区分。

### 国内研究现状

国内防火墙研究首先围绕配置错误识别和规则关系分析展开。王卫平、陈文惠于 2005 年分析常见规则配置错误，并讨论检测与处理方法[7]；李林、卢显良于 2006 年针对新增规则与已有规则的冲突，提出基于元组空间搜索的检测算法[8]。2015 年，殷奕、汪芸从集合包含关系入手解析规则间关系，为后续异常检测提供基础[9]。2017 年，王旭东等进一步研究带时间条件的多层防火墙 ACL 策略审计，将数据归一化、规则异常分析和结果记录组织为审计流程[10]。这一脉络表明，可靠审计既依赖匹配条件的准确表达，也依赖规则关系、动作和适用条件的共同分析。

2024 年，国内相关综述进一步系统梳理大模型工具学习与智能体构建方法。林衍凯梳理大模型工具学习的进展与挑战，讨论意图理解、规划、工具使用和记忆管理[11]；郭先会等围绕智能体的组成、任务规划、执行及有效性评估进行综述[12]。这些研究为本课题划分模型、工具、业务服务和执行记录的职责提供了参考，也支持将工具选择、调用结果利用和任务完成情况作为独立评价对象，而不是仅评价回答是否流畅。

2025 年，防火墙分析工具化与模型工具使用方法体系化继续发展。赖清楠提出 AT4FP，利用区间树和状态图等方法检测运行防火墙的安全策略异常，并讨论异常处理流程[13]，体现了将规则分析组织为实际检测工具的研究方向。郑逸宁等进一步梳理大语言模型工具使用的基本概念、发展过程、数据集和技术方法[14]，为选择工具交互方式与评价维度提供了较完整的中文参考。对本课题而言，前者支撑审计业务和检测工具设计，后者支撑受限智能体的工具调用与结果利用；二者结合的重点是工程协同，而不是简单用模型替换规则计算。

2026 年，康俊驰等从信息获取、分析定位和效果评估等阶段，综述大语言模型智能体在软件系统根因分析中的应用[15]。虽然该文研究对象并非防火墙策略，但其面向具体运维任务组织数据、工具和评估流程的思路，对本课题设计依赖上下文的证据补查具有参考价值。这些研究分别体现了防火墙策略分析工具化与智能体面向具体任务应用两个方向。本课题结合两条研究路径，重点解决云防火墙审计中的规则计算、业务上下文和证据补查如何协同的问题。

### 研究现状评述

综合上述研究，规则语义分析为可确定计算的配置问题提供了方法基础，工具增强智能体则为上下文获取和交互式任务处理提供了实现路径。本课题需要将三类问题衔接起来：一是将云平台配置转换为来源、版本和完整性明确的统一输入；二是区分配置事实、业务授权与模型推断，避免把资产线索或访问记录直接视为授权；三是把规则发现、证据补查、条件化建议与人工复审组织为可追溯的流程。规则关系分析不能替代业务需求确认，模型解释也不能替代确定性的语义计算。

因此，本课题以确定性规则与受限智能体协同为主线，连接云配置采集、业务要求确认、策略检查和推荐复审。在评价上，以仅规则方案提供确定性基线，对采用模型的固定流程与智能体方案统一初始概况、模型、工具权限和预算上限，重点比较证据利用、建议质量、信息不足处理及执行开销，分析动态补查的收益与代价，而不预先假定智能体必然优于固定流程。

## 相关技术介绍

本课题围绕策略分析、智能体执行、Web 交互和业务记录持久化组织技术方案，各部分通过统一数据模型与应用服务衔接，支撑后续需求分析和系统设计。

### 云防火墙策略与访问控制语义

云防火墙通过访问控制规则约束经过所审边界的网络流量。策略分析需要结合方向、协议、地址与端口范围、处理动作、优先顺序、启用状态、引用对象及默认行为，而不能只判断是否存在某一条允许规则。地址和端口范围可以转换为集合与区间，作为分析规则包含、相交及访问范围差异的基础[9]。本课题据此建立支持范围内的确定性判据，关联资产、防护状态及已确认业务要求；配置层面的允许关系不直接证明实际监听、端到端可达或业务授权。

### 大模型工具调用与 ReAct 智能体

工具调用将模型生成的结构化请求交给应用执行，并将查询结果返回模型。ReAct 将任务分析、行动和环境反馈交替组织，使后续行动能够依据中间结果调整[2]。本课题将资产、策略、业务要求及证据查询封装为只读工具，让智能体按需补查，而非一次性生成审计答案。工具的参数、对象范围与执行预算由后端校验，返回内容不能改变授权边界；最终结果分别保留规则事实、模型解释和待确认问题，以降低外部内容与错误推断对结论的影响[4]。

### Eino 智能体编排与 Go Web 服务

Go 后端负责数据接入、领域计算和应用服务；Gin 用于组织 HTTP 路由、JSON 请求处理及中间件，承担 Web 接口入口。Eino 用于组织模型与工具之间的交互循环，复用通用执行能力，而审计规则、证据引用、工具授权和业务状态仍由应用实现。这样既能保持 Go 技术栈的一致性，也能避免将规则逻辑和智能体执行过程直接写入接口处理函数。

在执行边界上，HTTP 请求负责接收和校验操作，耗时审计由受控任务工作器处理；业务会话与报告历史由应用数据层保存，不把框架执行上下文当作完整业务历史。云查询、模型调用及耗时的规范化计算设置超时或执行预算，并在数据库事务之外完成。

### Vue 与 TypeScript 前端开发

Vue 通过组件化与响应式机制组织用户界面，适合构建资产表格、确认表单、任务状态、证据详情和推荐审阅等交互。TypeScript 用于约束前端数据对象与接口使用方式，在开发阶段检查类型错误；Vite 承担开发服务与静态资源构建。本课题以前后端分离方式开发，前端通过受控接口展示数据和提交确认，云与模型凭据留在后端。静态类型检查不替代运行时的输入校验，策略事实、权限判断及业务版本校验仍由服务端负责。

### SQLite 数据存储与事务管理

SQLite 是嵌入式关系数据库，不需要额外部署独立数据库服务，适合本课题单机、小规模的业务记录持久化。数据访问遵循纯 Go 驱动约束，用于管理已确认业务版本、连续会话、任务和报告等关联记录。云平台接口只读并不意味着本地数据库只读，用户确认、消息保存与任务创建仍需要本地写入。

事务用于将相关操作作为一个整体提交，失败时回滚。例如，业务要求确认需在同一事务内复核基版本、创建确认后的版本并更新草稿状态；发送消息时，消息、轮次、幂等记录与待执行任务记录也需一致提交，避免只保存部分记录。沿用现有设计，数据库使用单连接与短事务，暂不启用 WAL。WAL 是日志模式选择，不是事务开关；不启用 WAL 仍可使用事务。云接口、模型请求和耗时计算放在事务外，事务只覆盖必要的本地读写，避免长时间占用数据库连接。

## 系统需求分析

系统面向运维或安全审计人员，围绕数据准备、业务确认、审计推荐和人工复审形成连续流程，主要需求如下。

（1）云平台接入与审计范围。面向阿里云云防火墙与 ECS，在明确授权的账号、地域和资源范围内只读采集资产、防护状态、策略及必要安全组上下文，同时支持离线快照导入。保留来源、分页和失败信息，不把缺权限或采集不完整解释为空配置。

（2）运行环境与模型接入。以单机 Web 为基本运行方式，云与模型连接显式配置、凭据留在后端，数据库遵循纯 Go 驱动约束。模型接入需验证多轮工具调用、结果关联、结构化输出及失败处理，不能仅以文本对话成功判断完整兼容。

（3）用户与业务流程。操作人员查看配置、确认画像和访问要求，再发起审计、查看证据与审阅建议。资产角色与访问授权分别确认，标签和端口不自动形成业务许可。审阅只保存本地处理意见；云上修改由人完成，复审使用新输入，不因用户标记“已处理”直接判定风险消除。

（4）系统功能与结果交付。提供资产和策略审阅、画像候选与业务要求维护、规则检查、智能体补查及报告复审，在支持范围内同时核对过宽放行与必要访问的配置差异。规则事实与模型疑点分列，建议说明对象、前提、证据和影响；模型失败时保留已得规则结果，并提供可阅读报告与结构化结果。

（5）数据与连续历史管理。支持固定快照、合格数据复用和强制刷新，保留各数据族时点、完整性和版本。业务草稿与确认版本分开，会话、可见消息、确认、任务、工具事件和报告关联持久化；审计固定所用数据、业务与规则版本，新增资料不覆盖旧结论，不持久化原始内部推理。

（6）安全与运行质量。本地接口设置访问保护与输入校验，对工具实施只读白名单、对象校验及轮次、总时限和调用量限制，外发模型的数据限于获准字段投影。显示排队至报告生成的阶段状态、错误和耗时，保存中断前的证据；续聊不自动重放旧的付费任务，页面提示不隐式扩大外部调用。

## 研究内容与方法

### 研究内容

本课题面向云上运维与安全审计人员，重点研究两个问题：如何将云配置、业务要求与检查依据关联为可复核的审计结论；在相同初始信息和工具权限下，智能体的动态补查能否改善推荐质量，其执行开销如何。主要研究内容包括以下五方面。

（1）云防火墙审计数据的建模与管理。关联阿里云云防火墙、ECS 和必要的安全组配置，将只读采集与离线快照转换为统一输入，记录来源、时点、完整性和版本。资产职责及业务访问要求经用户确认后保存，审计任务固定所用快照与业务版本，使历史结论能够追溯到当时的依据。

（2）基于策略语义的确定性审计。依据产品语义，分别开展选用安全基线检查与已确认业务要求的一致性检查，重点关注防护覆盖、过宽访问和重复规则候选。分析考虑方向、协议、地址与端口范围、动作、顺序、状态、引用及默认行为；原始发现独立保存，证据不足或超出支持范围时明确标注。

（3）受限智能体的证据补查与条件化推荐。提供资产上下文、策略详情、业务要求和证据查询等只读工具，由智能体依据返回结果选择后续补查。推荐说明修改对象、成立条件、证据与业务影响，缺少授权时保留待确认。模型解释与疑点单独记录，不覆盖规则原始发现；后端实施参数、对象范围与调用预算校验。

（4）审计与推荐系统的设计实现。采用前后端分离的 Web 形式，贯通数据准备、业务确认、任务执行、推荐审阅和报告生成。云与模型凭据由后端管理，持久化连续会话、确认记录、任务、公开工具事件及报告。策略由人手动应用，系统通过重新采集与审计支持整改后复审。

（5）系统测试与协同效果评价。组织正常、异常、业务例外和信息不足等案例，开展功能、策略语义、异常处理、安全和性能测试。对比仅规则、规则＋固定模型流程、规则＋智能体工具选择三种方式，分层评价规则发现、模型疑点和建议质量，记录工具与模型调用次数、端到端耗时，并通过云环境演示检验复审流程。

预期形成一套可演示的 Web 审计与推荐系统，配套统一审计数据约定、规则目录、可复核案例集、带证据的报告及对照评价记录。

### 研究方法

（1）文献研究与需求分析法。阅读防火墙规则分析、云网络配置验证、工具调用与智能体安全文献，结合云防火墙审计场景梳理使用者、输入输出和业务流程，将需求落实为数据管理、审计判据、人工确认及质量约束。

（2）策略语义建模与案例分析法。使用统一对象表达策略及其匹配条件，通过地址、端口和规则关系分析建立确定性判据；构造覆盖正常、冲突、例外与缺失信息的案例，逐项核对判据、证据和推荐边界，保持配置事实与业务授权分离。

（3）系统设计与迭代实现法。采用模块化方式分离云平台适配、数据归一化、规则审计、智能体编排和 Web 交互，设计持久化实体、接口及权限边界，通过原型评审、模块实现和集成测试逐步形成完整使用流程。

（4）对照实验与测试验证法。固定数据快照、业务版本及规则结果：固定流程按预设步骤获取上下文，智能体根据工具反馈选择查询；两种模型方案使用相同初始概况、模型、工具权限和预算上限。调试与评测案例分开，预先固定标签及问题去重口径；设置必须依赖前次返回结果才能继续补查的案例，核对实际工具事件。已确认问题与信息不足案例分别统计，建议质量由人工复核，并记录误报、漏报、失败与执行开销。


离线评价先以约20—30个小型人工构造案例为起点，预先标注目标问题、证据位置、应保持待确认的情形和可接受建议。对预先标注正常和异常的案例，按既定问题单元统计规则识别的查准率、查全率及误报漏报，信息不足样本单列；建议按对象正确、证据支持、符合业务约束和不引入超出已确认授权范围的额外开放四项判据人工复核，记录满足、不满足或无法判断。云环境演示用于核对采集、关联与复审流程，不以少量演示替代标注案例的效果评价。

## 论文组织结构

全文围绕云防火墙审计业务和智能体工程两条主线展开，共分为六章，各章安排如下。

第1章为绪论。说明课题背景、研究意义及国内外研究现状，归纳需要解决的问题，明确研究内容、研究方法和论文整体安排。

第2章为相关技术介绍。围绕后续需求与系统设计，介绍云防火墙策略语义、大模型工具调用与 ReAct 方法、Eino 与 Go Web 服务、Vue 与 TypeScript，以及 SQLite 数据存储与事务管理，为需求分析和模块设计提供技术基础。

第3章为系统需求分析。从云平台接入、运行环境、模型接口能力和用户使用流程出发，分析资产与策略管理、业务访问要求确认、审计推荐和报告复审需求，重点说明快照、业务版本、连续会话与历史记录的管理要求，以及安全、可靠性和性能约束。

第4章为系统设计。给出总体架构与模块职责，设计审计数据模型、策略归一化与规则检查、智能体工具调用及证据补查、条件化推荐与人工复审，并说明任务执行、连续会话、接口和安全控制。

第5章为系统实现与测试。介绍核心模块及其协同流程，开展功能、策略语义、异常处理、安全与性能测试，组织规则、固定模型流程和智能体的对照实验，结合云环境演示与修改后复审分析系统效果及局限。

第6章为总结与展望。总结研究工作和系统设计实现，结合实验与使用流程归纳适用范围及不足，提出后续改进方向。
