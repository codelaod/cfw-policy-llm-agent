# 开题报告

**论文题目：基于大模型智能体的云防火墙策略审计与推荐系统设计与实现**

## 选题背景与意义

在云上业务的日常运维中，访问控制策略会伴随应用上线、联调测试和故障排查不断调整。例如，为排查问题临时放开的管理端口，在处理结束后可能仍保留原有规则；业务迁移或服务器用途调整后，旧的访问范围也可能未同步更新。这些配置在创建时有具体用途，随着使用条件变化，却未必仍然合理。运维人员需要结合资产用途、访问范围和当前业务要求，持续核对云防火墙策略是否适当。

策略是否合理，取决于配置语义与业务背景的共同约束。同样的公网允许规则，对公共 Web 服务和内部数据库可能具有不同含义；管理端口是否应当开放，也取决于明确的运维来源。同时，多条规则的顺序、匹配范围、动作和默认行为共同决定配置层面的访问结果，不能仅凭单条规则判断整体效果。已有研究围绕规则冲突、遮蔽和冗余建立了分析方法[1]，但形成可供处置的结论，还需要关联资产职责、业务授权与数据完整性。

完成这样的审计，需要在资产信息、策略列表和业务说明之间逐项核对，还要解释修改配置后可能影响哪些访问。固定规则适合处理可确定计算的问题，业务背景的补充、证据的选择和整改影响的说明则需要进一步结合上下文。直接让大模型根据一份配置文本作答，又可能遗漏条件或补造业务需求。如何在确定性分析的基础上补充必要信息，并形成有依据、可复核的建议，由此成为值得研究的工程问题。

大模型智能体为这一过程提供了实现思路。ReAct 交替组织任务分析、行动和环境反馈，使模型能够根据中间结果继续选择行动[2]；Toolformer 展示了模型学习使用外部工具的可能性[3]。将资产查询、策略读取、引用展开和业务要求检索封装为受限工具，可以让模型依据查询结果继续补充信息，并为建议保留证据来源。与此同时，工具内容也可能携带间接提示注入[4]，权限控制和执行边界需要与智能体能力共同设计。

围绕上述需求，拟设计并实现一个面向公有云云防火墙的策略审计与推荐系统，贯通数据准备、业务确认、策略检查、推荐审阅和修改后复审。确定性规则负责明确语义下的配置检查，智能体负责按需补查证据、结合业务背景解释风险并形成条件化建议，策略由人确认后手动应用。统一数据模型、证据引用和连续历史记录用于保留判断依据，并通过对照实验分析规则与智能体协同的效果及适用条件。

将配置问题、业务依据和修改影响集中呈现，有助于运维人员理解审计结论、核对整改范围，并在修改后检查问题是否消除。对于缺少专职安全人员的团队，这样的辅助工具也有望减少重复的信息整理工作，使有限人力能够更多地投入业务确认与风险处置。通过可解释的检查、人工确认和结果留痕，探索大模型在安全运维中的应用方式，预期能够为减少配置疏漏、控制不当整改风险，以及维护数据安全和业务连续性提供实践参考。具体收益仍需通过后续测试与实验评价。

## 论文综述（综述国内外有关选题的研究动态）

### 国外研究现状

防火墙策略分析的一条重要思路，是将规则的匹配条件和处理动作转化为可以计算的关系。Al-Shaer 等对单个及分布式防火墙中的策略冲突进行分类，分析规则之间的关系，并提出相应的异常发现方法[1]。面向云环境，Backes 等将 AWS 网络配置作为分析输入，通过形式化方法判断网络可达性[5]。两项研究的对象分别侧重规则集与云网络配置，共同强调依据明确的配置语义开展分析，其结论依赖所采用的模型和输入范围。

模型如何获取和利用外部信息，是工具增强智能体研究的另一项核心问题。ReAct 将任务分析与行动交替组织，使模型能够根据环境反馈调整后续步骤[2]。Toolformer 则通过自监督学习，使模型学习何时调用外部 API、传入哪些参数以及如何利用返回结果[3]。前者着重交互过程的组织，后者着重工具使用能力的学习，二者分别从执行流程和模型训练层面探索语言模型与外部工具的结合。

在具体安全任务中，模型还需要处理多步骤执行和上下文保持问题。PentestGPT 围绕渗透测试组织大模型的任务流程，针对测试过程中容易丢失上下文的问题设置不同职责的模块，并结合测试任务评价其表现[6]。这类研究将评价对象从单次回答扩展到任务推进过程，关注模型能否持续利用已有信息、完成后续步骤。

外部工具同时引入了新的信任边界。InjecAgent 针对工具集成智能体构建间接提示注入评测，研究攻击者通过外部内容影响智能体行为的风险[4]。因此，模型能够读取工具结果，并不意味着这些内容可以获得指令权限。工具的访问范围、参数校验和结果处理，需要纳入智能体执行机制一并考虑。

### 国内研究现状

国内关于防火墙配置的研究，围绕错误检测和规则关系分析形成了多种方法。王卫平、陈文惠讨论规则配置错误的识别与检测[7]；李林、卢显良采用元组空间搜索，查找新增规则与已有规则集之间的冲突[8]；殷奕、汪芸则将规则建模，从集合关系出发解析包含关系[9]。这些方法分别处理错误识别、冲突查找和匹配范围表达等问题。其中，包含关系研究不考虑规则动作，因而在审计中还需要结合动作及执行顺序判断具体影响。

面向审计流程和检测工具，研究还需处理规则条件的完整表达与结果组织。王旭东等研究带时间约束的多层防火墙 ACL 策略审计，将归一化、异常分析和审计记录衔接起来[10]。赖清楠提出的 AT4FP 采用区间树和状态图等方法，将策略异常检测组织为可运行的工具[11]。从这些工作可以看到，形成可复核的审计应用，除了规则计算，还需组织审计输入、结果记录与验证流程。

在大模型工具使用与智能体构建方面，国内综述从不同层次整理了相关技术。林衍凯讨论工具学习中的意图理解、规划、工具使用和记忆管理等环节[12]；郭先会等梳理智能体构建方法及有效性评估[13]；郑逸宁等系统总结大语言模型工具使用的概念、技术方法与数据集[14]。这些综述将工具调用置于任务理解、执行和评价的整体过程中，有助于明确模型能力、应用流程与评估方法各自承担的作用。

智能体在运维分析中的应用，则进一步关注具体任务中的信息组织。康俊驰等围绕软件系统根因分析，从信息获取、根因定位和效果评估三个阶段梳理大语言模型智能体的应用[15]。其研究对象是故障根因定位，关注如何取得相关信息、组织分析过程并评价定位效果，体现了围绕实际任务设计智能体流程的研究思路。

### 研究现状评述

上述研究从不同层面支撑了策略审计与智能体应用：规则分析和云配置验证侧重既定语义下的访问关系，工具增强方法侧重外部信息获取与交互执行，安全任务和运维应用则关注多步骤任务的组织与评价。将这些方法用于云防火墙日常审计，还需要把配置事实与业务要求连接起来。例如，一条允许规则是否过宽，既涉及匹配范围，也涉及访问来源是否得到授权；模型取得的资产线索和工具结果，则需要明确来源及使用边界。渗透测试和根因定位中的任务效果，也需在策略审计场景下重新验证。

基于这些认识，研究拟围绕确定性规则与受限智能体的协同展开：先依据配置语义完成可重复的检查，再根据业务要求和信息缺口补查证据，生成说明适用条件的建议，并由人工审阅和复审。评价重点是审计结论能否追溯到配置与业务依据，以及动态补查对建议质量和执行开销有何影响。通过与规则基线、固定模型流程进行对比，检验这一协同方式的适用条件及局限。

## 相关技术介绍

系统的技术方案围绕策略分析、智能体执行、Web 交互和业务记录持久化展开，各部分通过统一数据模型与应用服务衔接。以下分别说明这些技术的基本原理及其在审计流程中的作用。

### 云防火墙策略与访问控制语义

云防火墙通过访问控制规则约束经过所审边界的网络流量。策略分析需要结合方向、协议、地址与端口范围、处理动作、优先顺序、启用状态、引用对象及默认行为。地址和端口范围可以转换为集合与区间，作为分析规则包含、相交及访问范围差异的基础[9]。规则引擎据此建立支持范围内的确定性判据，关联资产、防护状态及已确认业务要求。所得结论限定在配置层面；实际监听、端到端可达性和业务授权还需各自的证据支持。

### 大模型工具调用与 ReAct 智能体

工具调用将模型生成的结构化请求交给应用执行，并将查询结果返回模型。ReAct 的交互方式允许后续行动依据中间结果调整[2]。在审计流程中，资产、策略、业务要求及证据查询被封装为只读工具，供智能体按需补查。后端校验工具参数、对象范围与执行预算，并将返回内容作为待分析的数据；最终结果分别保留规则事实、模型解释和待确认问题。工具结果的处理与执行权限分开约束，以应对外部内容中的间接提示注入风险[4]。

### Eino 智能体编排与 Go Web 服务

Go 后端负责数据接入、领域计算和应用服务；Gin 用于组织 HTTP 路由、JSON 请求处理及中间件，承担 Web 接口入口。Eino 用于组织模型与工具之间的交互循环，复用通用执行能力，而审计规则、证据引用、工具授权和业务状态仍由应用实现。这样既能保持 Go 技术栈的一致性，也能避免将规则逻辑和智能体执行过程直接写入接口处理函数。

HTTP 请求负责接收和校验操作，耗时审计由受控任务工作器处理；应用数据层负责保存业务会话与报告历史，框架上下文仅用于对应的执行过程。云查询、模型调用及耗时的规范化计算设置超时或执行预算，并在数据库事务之外完成。

### Vue 与 TypeScript 前端开发

Vue 通过组件化与响应式机制组织用户界面，适合构建资产表格、确认表单、任务状态、证据详情和推荐审阅等交互。TypeScript 用于约束前端数据对象与接口使用方式，在开发阶段检查类型错误；Vite 承担开发服务与静态资源构建。在前后端分离的结构中，前端通过受控接口展示数据和提交确认，云与模型凭据留在后端。运行时输入、权限和业务版本仍由服务端校验，与开发阶段的静态类型检查共同约束接口的使用。

### SQLite 数据存储与事务管理

SQLite 是嵌入式关系数据库，不需要额外部署独立数据库服务，适合单机、小规模的业务记录持久化。系统拟采用纯 Go 驱动访问数据库，管理已确认业务版本、连续会话、任务和报告等关联记录。云平台配置通过只读接口获取，用户确认、消息保存与任务创建则通过本地数据库写入记录。

事务用于将相关操作作为一个整体提交，失败时回滚。例如，业务要求确认需在同一事务内复核基版本、创建确认后的版本并更新草稿状态；发送消息时，消息、轮次、幂等记录与待执行任务记录也需一致提交，保证关联记录的一致性。数据库拟使用单连接与短事务，暂不启用 WAL 日志模式。事务只覆盖必要的本地读写，云接口、模型请求和耗时计算在事务外完成，以控制数据库连接的占用时间。

## 系统需求分析

系统面向运维或安全审计人员，围绕数据准备、业务确认、审计推荐和人工复审形成连续流程，主要需求如下。

（1）云平台接入与审计范围。围绕公有云云防火墙的资产、防护状态与访问控制策略建立统一审计输入，首版选用阿里云云防火墙及配套 ECS 作为接入与演示验证环境，以便按实验规模和使用周期控制资源成本。在明确授权的账号、地域和资源范围内只读采集配置及必要安全组上下文，同时支持离线快照导入。保留来源、分页和失败信息，不把缺权限或采集不完整解释为空配置。其他云平台的接口适配与策略语义另需验证，不属于首版已支持能力。

（2）运行环境与模型接入。以单机 Web 为基本运行方式，云与模型连接显式配置、凭据留在后端，数据库遵循纯 Go 驱动约束。模型接入需验证多轮工具调用、结果关联、结构化输出及失败处理，不能仅以文本对话成功判断完整兼容。

（3）用户与业务流程。操作人员查看配置、确认画像和访问要求，再发起审计、查看证据与审阅建议。资产角色与访问授权分别确认，标签和端口不自动形成业务许可。审阅只保存本地处理意见；云上修改由人完成，复审使用新输入，不因用户标记“已处理”直接判定风险消除。

（4）系统功能与结果交付。提供资产和策略审阅、画像候选与业务要求维护、规则检查、智能体补查及报告复审，在支持范围内同时核对过宽放行与必要访问的配置差异。规则事实与模型疑点分列，建议说明对象、前提、证据和影响；模型失败时保留已得规则结果，并提供可阅读报告与结构化结果。

（5）数据与连续历史管理。支持固定快照、合格数据复用和强制刷新，保留各数据族时点、完整性和版本。业务草稿与确认版本分开，会话、可见消息、确认、任务、工具事件和报告关联持久化；审计固定所用数据、业务与规则版本，新增资料不覆盖旧结论，不持久化原始内部推理。

（6）安全与运行质量。本地接口设置访问保护与输入校验，对工具实施只读白名单、对象校验及轮次、总时限和调用量限制，外发模型的数据限于获准字段投影。显示排队至报告生成的阶段状态、错误和耗时，保存中断前的证据；续聊不自动重放旧的付费任务，页面提示不隐式扩大外部调用。

## 研究内容与方法

### 研究内容

围绕云上运维与安全审计需求，研究聚焦两个问题：如何将云配置、业务要求与检查依据关联为可复核的审计结论；在相同初始信息和工具权限下，智能体的动态补查能否改善推荐质量，其执行开销如何。具体工作包括以下五方面。

（1）云防火墙审计数据的建模与管理。关联云防火墙策略、云服务器资产和必要的安全组配置，将只读采集与离线快照转换为统一输入，记录来源、时点、完整性和版本。首版通过阿里云相关接口完成适配与验证，接口与字段差异由适配层处理，规则检查保留所用产品语义与支持范围。资产职责及业务访问要求经用户确认后保存，审计任务固定所用快照与业务版本，使历史结论能够追溯到当时的依据。

（2）基于策略语义的确定性审计。依据产品语义，分别开展选用安全基线检查与已确认业务要求的一致性检查，重点关注防护覆盖、过宽访问和重复规则候选。分析考虑方向、协议、地址与端口范围、动作、顺序、状态、引用及默认行为；原始发现独立保存，证据不足或超出支持范围时明确标注。

（3）受限智能体的证据补查与条件化推荐。提供资产上下文、策略详情、业务要求和证据查询等只读工具，由智能体依据返回结果选择后续补查。推荐说明修改对象、成立条件、证据与业务影响，缺少明确的业务授权依据时保留待确认。模型解释与疑点单独记录，不覆盖规则原始发现；后端实施参数、对象范围与调用预算校验。

（4）审计与推荐系统的设计实现。采用前后端分离的 Web 形式，贯通数据准备、业务确认、任务执行、推荐审阅和报告生成。云与模型凭据由后端管理，持久化连续会话、确认记录、任务、用户可见的工具事件摘要及报告。策略由人手动应用，系统通过重新采集与审计支持整改后复审。

（5）系统测试与协同效果评价。组织正常、异常、业务例外和信息不足等案例，开展功能、策略语义、异常处理、安全和性能测试。对比仅规则、规则＋固定模型流程、规则＋智能体工具选择三种方式，分层评价规则发现、模型疑点和建议质量，记录工具与模型调用次数、端到端耗时，并通过云环境演示检验复审流程。

预期形成一套可演示的 Web 审计与推荐系统，配套统一审计数据约定、规则目录、可复核案例集、带证据的报告及对照评价记录。

### 研究方法

（1）文献研究与需求分析法。阅读防火墙规则分析、云网络配置验证、工具调用与智能体安全文献，结合云防火墙审计场景梳理使用者、输入输出和业务流程，将需求落实为数据管理、审计判据、人工确认及质量约束。

（2）策略语义建模与案例分析法。使用统一对象表达策略及其匹配条件，通过地址、端口和规则关系分析建立确定性判据；构造覆盖正常、冲突、例外与缺失信息的案例，逐项核对判据、证据和推荐边界，保持配置事实与业务授权分离。

（3）系统设计与迭代实现法。采用模块化方式分离云平台适配、数据归一化、规则审计、智能体编排和 Web 交互，设计持久化实体、接口及权限边界，通过原型评审、模块实现和集成测试逐步形成完整使用流程。

（4）对照实验与测试验证法。固定数据快照、业务版本及规则结果：固定流程按预设步骤获取上下文，智能体根据工具反馈选择查询；两种模型方案使用相同初始概况、模型、工具权限和预算上限。调试与评测案例分开，预先固定标签及问题去重口径；设置必须依赖前次返回结果才能继续补查的案例，核对实际工具事件。已确认问题与信息不足案例分别统计，建议质量由人工复核，并记录误报、漏报、失败与执行开销。


离线评价先以约20—30个小型人工构造案例为起点，预先标注目标问题、证据位置、应保持待确认的情形和可接受建议。对预先标注正常和异常的案例，按既定问题单元统计规则识别的查准率、查全率及误报漏报，信息不足样本单列；建议按对象正确、证据支持、符合业务约束和不引入超出已确认授权范围的额外开放四项判据人工复核，记录满足、不满足或无法判断。云环境演示用于核对采集、关联与复审流程，不以少量演示替代标注案例的效果评价。

## 论文组织结构

全文围绕云防火墙审计业务和智能体工程两条主线展开，共分为六章，各章安排如下。

第1章为绪论。说明课题背景、研究意义及国内外研究现状，归纳需要解决的问题，明确研究内容、研究方法和论文整体安排。

第2章为相关技术介绍。围绕后续需求与系统设计，介绍云防火墙策略语义、大模型工具调用与 ReAct 方法、Eino 与 Go Web 服务、Vue 与 TypeScript，以及 SQLite 数据存储与事务管理，为需求分析和模块设计提供技术基础。

第3章为系统需求分析。从云平台接入、运行环境、模型接口能力和用户使用流程出发，分析资产与策略管理、业务访问要求确认、审计推荐和报告复审需求，重点说明快照、业务版本、连续会话与历史记录的管理要求，以及安全、可靠性和性能约束。

第4章为系统设计。给出总体架构与模块职责，设计审计数据模型、策略归一化与规则检查、智能体工具调用及证据补查、条件化推荐与人工复审，并说明任务执行、连续会话、接口和安全控制。

第5章为系统实现与测试。介绍核心模块及其协同流程，开展功能、策略语义、异常处理、安全与性能测试，组织规则、固定模型流程和智能体的对照实验，结合云环境演示与修改后复审分析系统效果及局限。

第6章为总结与展望。总结研究工作和系统设计实现，结合实验与使用流程归纳适用范围及不足，提出后续改进方向。
